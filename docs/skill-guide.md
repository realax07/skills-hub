# Как писать скиллы в skills-hub

Сжатая, агент-нейтральная версия гайда skill-creator от Anthropic
и спецификации [Agent Skills](https://agentskills.io). Применимо к любому агенту из `agents.conf`.

## Анатомия скилла

```
<тема>/skills/<skill-name>/
├── SKILL.md          обязателен: frontmatter (name, description) + инструкции
├── references/       правила и справка — агент читает по необходимости
│   └── rules.md
├── examples/         разобранные примеры вход → ход работы → результат, хорошо/плохо
├── scripts/          исполняемый код для детерминированных и повторяющихся шагов
│   └── setup.mjs     (если есть зависимости) установщик, см. «Зависимости»
├── assets/           файлы для результата: шаблоны, иконки, шрифты, конфиги
└── evals/            тест-кейсы скилла (агентам не ставятся)
    └── <case-name>/
        ├── prompt.md
        ├── case.yaml
        ├── graders/01-*.md
        └── files/    (входные файлы, если нужны)
```

Создавать так: `python3 tools/new_skill.py <тема> <имя>` — скопирует `_template/skill-name` со всей структурой.
Ненужные папки можно удалить, но `evals/` оставляй.

## Прогрессивная загрузка — главный принцип

Агент грузит скилл в три уровня, и структура должна это уважать:

1. **name + description** — всегда в контексте (~100 слов). По ним агент решает, брать ли скилл.
2. **Тело SKILL.md** — загружается, когда скилл сработал. Держи до ~500 строк.
3. **references / examples / scripts / assets** — только когда нужны. Объём не ограничен; скрипты можно запускать, не читая.

Поэтому: в SKILL.md — процесс, ключевые правила и короткий пример; всё подробное — в `references/`
и `examples/`, **с явным указанием, когда какой файл открывать**. Справочник длиннее ~300 строк — с оглавлением.
Скилл под несколько вариантов (фреймворки, платформы) — по файлу на вариант: `references/react.md`, `references/vue.md`.

## description — механизм срабатывания

- Что делает **и когда применять**: фразы, контексты, типы задач, границы «не применяй для…». Вся информация «когда» — здесь, не в теле:
  в теле SKILL.md раздела «когда применять» нет, тело — только про выполнение задачи.
- Агенты склонны *не* брать скиллы, поэтому формулируй чуть настойчиво:
  «…Используй, когда пользователь просит лендинг, hero-блок, редизайн страницы — даже если не говорит слово "дизайн"».
- До 1024 символов, одной строкой, без `<` `>`. `name` — kebab-case, совпадает с папкой, уникален в репо.

## Как писать инструкции

- Повелительное наклонение: «Проверь…», «Сгенерируй…».
- **Объясняй почему.** Вместо капсового ВСЕГДА/НИКОГДА — причина. Модель, понимающая цель, сама обработает крайние случаи.
- Общие принципы, а не подгонка под пару примеров: скилл будут вызывать на тысячах разных запросов.
- Строгий формат результата — точным шаблоном (в теле или в `assets/`).
- Без привязки к одному агенту: не упоминай инструменты конкретного агента, пути — относительно папки скилла.

### Под любые модели

Скиллы хаба запускают не только сильные модели: DeepSeek, GLM Flash, Kimi, Codex, Claude — в том числе быстрые и без зрения.
Пиши так, чтобы скилл проходил на самой слабой из них: сильная от явности не пострадает, слабая без неё ошибётся.

- **Точные команды.** Полная команда с плейсхолдерами (`node <skill>/scripts/x.mjs <out> --json`), а не «запусти скрипт разведки».
  Слабая модель не достроит недостающий флаг, а придумает свой.
- **Шаги по порядку, развилки явно.** Нумерованный процесс; у каждого решения — условие и вариант по умолчанию
  («нет X — делай Y»). Чего нельзя решать за пользователя — так и написано, с поведением «спросить некого»
  (автономный прогон): что оставить незаданным и что написать в отчёте.
- **Детерминированное — в скрипты.** Всё, где можно ошибиться руками (правка JSON, подсчёты, разбор вывода), —
  CLI с проверкой аргументов и понятной ошибкой. Суждение оставь модели, механику — коду.
- **Без обязательного зрения.** Если шаг опирается на картинки или скриншоты — дай текстовую альтернативу
  (список со значениями, `--json`): часть моделей изображений не видит.
- **Таблица «Если что-то не так».** Симптом → что делать. Иначе слабая модель обходит ошибку вручную и портит результат.
- **Проверка результата шагом процесса.** Команда проверки и критерий «готово» — чтобы модель не объявляла успех на глаз.

## Правила (`references/`)

Обязательные правила с причинами, рекомендации, таблица крайних случаев, типичные ошибки.
Шаблон — `_template/skill-name/references/rules.md`.

## Примеры (`examples/`)

Один файл — один пример: реалистичный запрос, ход работы, результат целиком, почему так.
Обязательно хотя бы один пример «плохо / хорошо» на крайний случай — это лучше всего калибрует качество.

## Скрипты (`scripts/`)

Если на тестах агент каждый раз пишет одинаковый вспомогательный код — это кандидат в `scripts/`.

- Python 3.9+ или Node.js 18+ только со стандартной библиотекой; всё остальное — через `compatibility` и `scripts/setup.*` (см. «Зависимости»).
- Кроссплатформенно (pathlib, без bash-специфики), `--help`, ненулевой код при ошибке, `--json` для машинного вывода.
- В SKILL.md — как вызвать и что вернёт: `python3 scripts/x.py <вход> --json`.

## Зависимости

Скиллы раскатываются на любые машины, поэтому всё, что не входит в стандартную библиотеку, объявляется и ставится явно:

- **`compatibility`** во frontmatter — что нужно (рантайм, пакеты, браузеры) и сколько весит.
- **Проверка — реальным вызовом, а не по путям.** Зависимость может уже стоять где угодно: в проекте, глобально,
  в другом кэше, системный браузер. Поэтому `setup` ищет её так, как найдёт рантайм в окружении агента, и **вызывает**
  (импорт, запуск браузера, `--version`). Работает — ставить нечего. Не завязывайся на конкретный путь установки.
- **`scripts/setup.mjs`** (или `setup.py` / `setup.sh`) — идемпотентный установщик:
  без аргументов ставит, с `--check` только проверяет (код 0/1), понятно пишет, чего не хватает.
- Ставь **вне папки скилла** — в `~/.cache/agent-skills/<skill>/` (Windows: `%LOCALAPPDATA%\agent-skills\<skill>\`):
  скилл бывает симлинком в git-репо или read-only копией. Путь можно переопределить переменной окружения.
- Версии пиннуй — одинаковое поведение на всех машинах.
- Системное (Node.js, Python, sudo-пакеты) не ставь молча: проверь и скажи, что поставить.
- Без аргументов `setup` сначала проверяет и ставит **только если проверка не прошла**; `--check` — только проверка (код 0/1);
  `--force` — поставить в кэш принудительно.
- В SKILL.md первым шагом процесса — `setup` (он сам проверит), при ошибке — таблица «Если что-то не так».

Хаб знает это соглашение: `./install.sh install --deps` ставит скиллы вместе с зависимостями,
`./install.sh deps [--check]` — только зависимости. После `install` хаб сам запускает `setup --check` каждого скилла
и подсказывает `deps` только тем, у кого проверка не прошла. Пример — `project-context/skills/web-design-context`.

## Тесты (`evals/`)

2–3 реалистичных запроса — так, как их напишет живой человек (с контекстом, путями, опечатками).
Формат совместим с `claude plugin eval`:

- `prompt.md` — блок настроек `--- ... ---`, затем запрос. Свободного текста в блоке настроек не должно быть.
- `case.yaml` — `schema_version: "1.1"` (в кавычках!), `name` = имя папки, `expected_outcome: |`.
- `graders/NN-что-проверяет.md` — блок `type: llm / focus: trace / weight: 1`, затем одно проверяемое утверждение о результате.
- Входные файлы — в `files/`, плюс `place-files.sh` и `context.scaffold_script` в `case.yaml`.

Субъективные скиллы (стиль, дизайн) проверяй глазами — не выдумывай формальные проверки там, где нужно суждение.

## Цикл работы

1. Понять задачу: что скилл даёт, когда срабатывает, какой результат.
2. Черновик: `tools/new_skill.py`, заполнить SKILL.md, правила, примеры.
3. Прогнать тестовые запросы со скиллом и без — сравнить. Если доступна слабая модель — прогони и на ней:
   её ошибки показывают, где инструкции неявны.
4. Улучшить по результатам: обобщать, убирать лишнее, выносить повторяющийся код в `scripts/`.
5. `python3 tools/validate.py <путь> --strict` → установить → повторять.

## Безопасность

Скилл не должен удивлять: его содержимое соответствует описанию.
Никакой скрытой отправки данных, вредоносного кода, обхода защит.
