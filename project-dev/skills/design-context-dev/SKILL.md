# Design Context Dev

Новая фича в существующем интерфейсе должна выглядеть так, будто её сделала та же команда. Дизайн-контекст
(`design-context/`) говорит, что принято: токены, канонические детали, схемы разделов, где это в коде. Этот скилл
делает по нему изменение и **проверяет результат измеримо**: тот же код извлечения, что снимал контекст, смотрит
на новую страницу, а скрипт сравнивает с каноном. «Выглядит как здесь» перестаёт быть делом вкуса.

## Как выполнять

Для любой модели: шаги по порядку, команды как написано (`<skill>` — папка этого скилла). Не придумывай флаги —
у скриптов есть `--help`. Скрипт упал — смотри «Если что-то не так», не обходи вручную.

## Процесс

1. **Зависимости.** `node <skill>/scripts/setup.mjs` — сам проверит реальным запуском браузера и поставит, только если не работает.
   Все строки с ✓ — дальше; осталась ✗ — таблица «Если что-то не так».

2. **Найди контекст.** Обычно `design-context/` в корне репозитория; путь есть в блоке `web-design-context` в AGENTS.md / CLAUDE.md.
   - **Нет контекста** (`brief.mjs` выходит с кодом 2) — скажи пользователю и предложи собрать его скиллом web-design-context.
     Ждать ответа нельзя или пользователь просит сделать сразу — делай по самой похожей существующей странице: те же классы,
     переменные и разметка, новых цветов и шрифтов не вводи. Шаги 3 и 6 пропусти (без контекста скрипты не работают),
     в отчёте прямо скажи, что проверки соответствия не было.

3. **Выжимка под задачу.**
   `node <skill>/scripts/brief.mjs --context design-context --path <URL-путь, который меняешь> --groups <нужные группы>`
   Получишь: позицию проекта, токены с именами переменных, канон деталей с разметкой и исходником, какую схему раздела открыть,
   компоненты и модалки, где это в коде, свежесть контекста. Затем открой **одну** схему раздела, которую назвал brief
   (`compositions/<раздел>.md`), и `source.md`, если меняешь код компонентов. Остальное — по необходимости.

4. **Реши, из чего собирать** — до кода, по позиции проекта (`stance`):
   - `normalize` — только варианты со статусом «канон». `preserve` — ближайший существующий вариант буквально.
     Не задана — самые частые варианты, в отчёте попроси владельца задать позицию.
   - Каждый новый элемент сопоставь с каноном: кнопка → какая кнопка из `parts/buttons.md`, карточка → какая карточка.
   - Нужного элемента в контексте нет (переключатель, таблица, степпер) — собери из токенов (цвета, шрифты, радиусы из выжимки),
     похожим на ближайшую деталь; в отчёте назови его новым и почему. Если спросить пользователя можно — спроси до вёрстки.
   - Иерархия действий: главное действие блока — основная кнопка, второстепенные — вторичная/контурная. Есть на сайте похожий блок
     (карточки, тарифы) — повтори его выбор кнопок. Заголовок блока — как у соседних секций в схеме раздела (тот же тег и размер).
   - Новые цвета, шрифты, тени не вводи. Нужен цвет, которого нет, — это решение владельца: спроси.
   - **Спросить некого** (автономный прогон) — не жди: возьми ближайшее из канона и палитры, а в отчёте отдельным пунктом:
     вопрос, что выбрано вместо просьбы пользователя и почему (например, «зелёного в палитре нет — взят основной синий»).

5. **Реализуй в коде проекта.** Через то, что уже есть: компоненты из `source.md` (папки примитивов `ui/` и т.п.),
   CSS-переменные из `design-context/assets/tokens.css` и `design-context/source.md`, существующие классы и утилиты. Не копируй вычисленные стили со страницы
   литералами — в коде должны быть те же переменные и компоненты, что у соседей. Файлы в `design-context/` не правь — они генерируются.

6. **Проверь.** Подними сайт (dev-сервер или сборка) и запусти:
   `node <skill>/scripts/check.mjs --context design-context --url <адрес страницы> --selector "<CSS нового блока>" --changed`
   (статика или сборка без сервера: `--serve site --path /about.html` — путь как имя файла; модалка: `--steps '[{"click":"…"},{"waitFor":"…"}]'`).
   - Интерактив (табы, меню, модалка) — проверь каждое состояние: ещё один запуск с `--steps`, открывающими его.
   - `✗` — нарушение: исправь по подсказке `→` и запусти снова. `!` — предупреждение: исправь или объясни в отчёте.
   - До 3 кругов. Осталось нарушение, которое нельзя убрать (новый элемент без канона, решение пользователя) — оставь и объясни.
   - Модель видит изображения — добавь `--shot <временная папка>/check.png` (не в проект) и сравни с соседними блоками глазами.
     Не видит — достаточно отчёта скрипта.
   - `✗ ошибка JS на странице` — скрипт проекта упал (часто ищет элемент, которого нет на новой странице): почини, не прячь.
   - Нужен мобильный вид — тот же запуск с `--viewport mobile`.

7. **Отчёт пользователю.** Что сделано и где (файлы); из каких канонических деталей собрано; итог `check.mjs`
   (нарушений / предупреждений, что осталось и почему); новые элементы без канона; предложение обновить контекст
   после слияния (web-design-context: добавить страницу в план и `capture.mjs --only <id>`).

## Ключевые правила

- **Канон, а не «похоже».** Новый элемент — существующий вариант из `parts/`, а не свой со «чуть другими» отступами:
  каждый такой вариант добавляет шум, который потом размножат другие агенты.
- **Переменные и компоненты, не литералы.** Значение в вычисленном стиле — `#3b5bdb`, в коде — `var(--color-primary)` или `<Button>`:
  иначе следующая смена темы обойдёт новое место.
- **Проверка скриптом обязательна.** Без неё «сделал в стиле» — мнение; `check.mjs` даёт факты и для моделей без зрения.
- **Решения владельца не принимай молча:** новые цвета и шрифты, отступление от позиции проекта, новый вариант вместо канона.
- **Контекст — снимок.** brief предупреждает, если после съёмки в исходниках были коммиты; противоречие контекста и текущего кода —
  верь коду для «как сделать», контексту — для «как должно выглядеть», и скажи об этом в отчёте.
- Подробно: [references/rules.md](references/rules.md).

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `brief`/`check`: «нет дизайн-контекста», код 2 | контекст не собран или путь не тот: найди `GUIDE.md` (блок в AGENTS.md); нет — ветка «Нет контекста» в шаге 2 |
| `brief`: «после даты съёмки N коммитов» | контекст мог устареть: посмотри названия коммитов; новые компоненты или стили — сверь `source.md` с кодом |
| `--serve`: страница 404 или пустая | путь как файл: `--path /about.html`, а не `/about` |
| одинаковые файлы в двух местах (`source.md` → «Копии файлов») | правь исходник; копию в сборке — только если сборки нет и обе подключены на страницах |
| `check`: «нет элемента <selector>» | селектор нового блока неверный или блок появляется после действия — поправь `--selector`, добавь `--steps` |
| `check`: «элементов 0» | страница не открылась или блок скрыт: проверь адрес, `--storage-state` для страниц за логином |
| `✗ новый вариант` у элемента, которого нет в каноне вовсе | так и есть: собери по токенам, объясни в отчёте (шаг 4) |
| `✗ цвет … не из палитры` в коде, а на странице всё ок | литерал в коде, который не попал на страницу (другое состояние) — всё равно замени на переменную |
| `✗ литерал #… → замени на var(--…)` | замени в указанной строке; переменная уже есть в проекте |
| много `✗` у старых элементов страницы | проверяй только новый блок: `--selector`; старое — не твоя задача, упомяни в отчёте |
| `--changed`: «не git-репозиторий» | проверь страницу без `--changed`, код — по правилам шага 5 вручную |
| `setup` нашёл Playwright «в кэше скиллов» или «в проекте» | так и задумано: годится любой работающий, общий с web-design-context ставится один раз |
| `setup` падает | `node <skill>/scripts/setup.mjs --with-deps` (Linux, sudo) или попроси пользователя |

## Пример

**Запрос:** «добавь на главную блок с тарифами, три тарифа с ценой и кнопкой, в том же стиле».
**Ход:** brief `--path / --groups buttons,cards` → канон: «Карточка», «Кнопка основная», «Кнопка контурная» →
блок из `.card` и `.btn btn-primary` / `.btn btn-ghost` в `index.html` → check `--selector "#pricing" --changed`:
✗ «h3 22px не из шкалы», ✗ «литерал #3b5bdb → var(--color-primary)» → исправлено → 0 нарушений → отчёт.

- [examples/01-pricing-block.md](examples/01-pricing-block.md) — полный проход: выжимка, вёрстка, два круга проверки
- [examples/02-no-canon-element.md](examples/02-no-canon-element.md) — элемент без канона и новый цвет: плохо и хорошо
