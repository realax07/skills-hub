# Пример 3: три варианта на выбор и тёмная тема

## Запрос

> Хочу на главной блок с тарифами. Перед тем как верстать, покажи три разных варианта. У сайта есть тёмная тема.

В контексте: позиция `normalize`; канон — `.card`, `.btn btn-primary`, `.btn btn-ghost`; в `foundations.md` раздел «Темы»:
`dark` включается классом `dark` на `<html>`, меняются `--color-text`, `--color-primary`, `--color-bg`, `--color-border`.

## Плохо

Сразу сверстать в `index.html` три блока подряд: три одинаковые карточки, у второго варианта синие кнопки, у третьего — зелёные.
Заголовок блока `color: #1f2328` «как у соседей», рамка `#e5e7eb`. Проверить только в светлой теме и выбрать вариант самому.

Почему плохо:
- Это один вариант в трёх цветах: пользователю не из чего выбирать по сути (сценарий тот же).
- Зелёный — новый цвет: новая система внутри фичи, решение владельца.
- `#1f2328` и `#e5e7eb` — значения переменных светлой темы литералами: в тёмной заголовок станет тёмным на тёмном фоне.
- Варианты в коде проекта до выбора — лишняя работа и мусор в диффе; выбор сделан за пользователя.

## Хорошо

```bash
node <skill>/scripts/brief.mjs --context design-context --path / --groups buttons,cards
# … ## Темы: dark (класс dark на <html>): --color-text: #1f2328 → #e6e8eb, --color-primary: #3b5bdb → #7c9cff, …
node <skill>/scripts/mock.mjs new --context design-context --out design-mocks/pricing --page home --where "#cards" --position after
```

PLAN.md до вёрстки — три **разных подхода** из `references/mock-patterns.md`, строка «Тарифы»:

| | Подход (UX) | Композиция | Палитра |
|---|---|---|---|
| A | карточки рядом, рекомендуемая с основной кнопкой | три колонки `.card` | светлая подложка |
| B | таблица сравнения возможностей | одна широкая таблица, плотно | светлая, границы `var(--color-border)` |
| C | переключатель месяц/год + одна крупная карточка | две колонки: довод и карточка | тёмная секция — фон футера сайта |

Фрагменты — только канон и переменные: `color: var(--color-text)`, `border-bottom: 1px solid var(--color-border)`,
кнопки `<button class="btn btn-primary">`. Затем:

```bash
node <skill>/scripts/mock.mjs build --out design-mocks/pricing
```

```
A: НЕ ПРОЙДЕНО — нарушений 1 (темы: основная + dark)
  ✗ кнопка «Начать» — новый вариант, такого на сайте нет (2 эл.)
      → ближайший вариант: … — отличие: подчёркивание underline вместо —
C: НЕ ПРОЙДЕНО — нарушений 1 (темы: основная + dark)
  ✗ [тема dark] цвет (текст) #1f2328 остался как в основной теме — 1 эл.
      → это значение --color-text: в коде литерал вместо var(--color-text) — тогда в теме dark станет `#e6e8eb`
Различие вариантов:
  ✓ AB: различаются (общее: одно использование палитры …)
  ✓ AC: различаются
  ✓ BC: различаются
```

Исправлено: `<a class="btn btn-ghost">` → `<button class="btn btn-ghost">` (у ссылки браузерное подчёркивание — это другой вариант);
литерал в C → `var(--color-text)`. Повторный `build` — `пройдено`.

Отчёт: «Три варианта — `design-mocks/pricing/index.html` (скриншоты в странице, плюсы и минусы, итог проверки во всех темах).
Рекомендую A: на лендинге важнее быстро сравнить цены; B — если тарифы различаются функциями. Какой берём?»
Код проекта не менялся. После ответа — реализация выбранного (шаг 5) и check.mjs по `index.html` с `--changed`.

## Почему так

- Подходы разные по сценарию, поэтому выбор осмысленный; палитра у C другая — из той же палитры сайта.
- Тёмная тема проверена до показа: литерал в C пойман скриптом, а не пользователем после релиза.
- Варианты собраны в странице эталона: видно, как блок стоит между карточками и футером.
