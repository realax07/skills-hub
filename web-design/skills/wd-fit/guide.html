Веб-дизайн · wd-fit

wd-fit: новое в интерфейсе — так, будто сделала та же команда

Скилл делает доработку существующего сайта по дизайн-контексту из wd-scan: берёт выжимку канона под задачу, по запросу показывает три разных мокапа прямо в странице сайта, реализует через существующие переменные и компоненты и проверяет результат скриптом во всех темах.

Что даёт

«Выглядит как здесь» перестаёт быть делом вкуса: те же скрипты, что снимали контекст, смотрят на новую страницу и сравнивают с каноном.

Выжимка под задачу

brief.mjs: позиция проекта, токены с именами переменных, канон нужных групп деталей с разметкой и исходником, какую схему раздела открыть, свежесть контекста.

Три мокапа на выбор

Когда просят варианты: три разных подхода к UX (не три цвета одной раскладки), собранных в настоящей странице сайта, с проверкой и страницей сравнения.

Реализация через канон

Новый элемент — существующий вариант из parts/; цвета — var(--…), компоненты — те, что уже есть в коде.

Проверка в браузере

check.mjs: цвета и шрифты вне палитры, новые варианты кнопок вместо канона, литералы вместо переменных, ошибки JS — во всех темах сайта, с подсказкой, что заменить.

Работает без зрения

Отчёт проверки — текстом с номерами строк и подсказками →. Скриншот — по желанию, если модель видит изображения.

Когда звать

Каждая доработка интерфейса после того, как wd-scan собрал контекст.

Подходит

  • «Добавь блок тарифов, в том же стиле», «новая страница как у нас», «чтобы не выбивалось».
  • «Покажи пару вариантов, как это может выглядеть» — мокапы на утверждение.
  • Проверить, что уже свёрстанное соответствует дизайну проекта.
  • В репозитории есть design-context/, даже если пользователь его не упомянул.

Не подходит

  • Дизайна ещё нет — wd-forge.
  • Контекста нет — сначала wd-scan (без него скилл делает по самой похожей странице и честно пишет, что проверки не было).
  • Редизайн всего сайта — это новое направление, а не доработка.

Как работает

Модель решает, из чего собрать, и верстает; скрипты дают выжимку, собирают мокапы и проверяют; выбор варианта и новые цвета — решения владельца.

Мелкая правка

Когда: поле, кнопка, строка

Сразу реализация и проверка: три мокапа утроили бы работу.

Крупная доработка с выбором

Когда: новый раздел, сценарий, «покажи варианты»

Сначала три мокапа на утверждение, реализуется только выбранный.

Без контекста

Когда: design-context/ нет

Предложить wd-scan; если делать сразу — по самой похожей странице, без новых цветов и шрифтов, с пометкой «проверки не было».

Как результат используется потом

Человек

Выбирает вариант в index.html, решает про новые цвета и элементы без канона, ревьюит отчёт проверки.

Следующий агент

Находит новый блок в коде собранным из тех же компонентов и переменных — шум не размножается.

Примеры из прогонов

Из разобранного прогона «блок тарифов на главной» (examples/01-pricing-block.md).

Каждый элемент задачи сопоставлен с каноном до кода.

brief.mjs --context design-context --path / --groups buttons,cards,badges
  позиция: приводить к канону
  цвета: #3b5bdb var(--color-primary), #1f2328 var(--color-text); шрифт Georgia
  канон: «Кнопка основная» .btn.btn-primary · «Кнопка контурная» .btn.btn-ghost · «Карточка» article.card · бейдж .badge
  схема раздела: compositions/home.md (hero → #cards → футер)

тариф → «Карточка»; «Выбрать» → «Кнопка основная»;
«Связаться» у «Бизнес» → «Кнопка контурная» (второстепенное действие); «новое» → бейдж

Проверка поймала то, что глазами не видно.

check.mjs --context design-context --serve site --path / --selector "#pricing" --changed
✗ литерал #3b5bdb в site/index.html:12
    → замени на var(--color-primary)
! сочетание шрифта Georgia 22px / 700 не встречается на сайте — 3 эл. (например h3 «Старт»)
    → размеры этого шрифта на сайте: 12px … 18.72px, 20px, 24px …; ближайшие — 20px, 24px

(исправлено: размер h3 как у соседних карточек, цена через var(--color-primary))

Главные правила

Почему скилл ведёт себя так, а не иначе.

  • Канон, а не «похоже».Каждый «чуть другой» вариант добавляет шум, который потом размножат другие агенты.
  • Переменные и компоненты, не литералы.Иначе следующая смена темы обойдёт новое место — проверка ловит это во второй теме.
  • Проверка скриптом обязательна.Без неё «сделал в стиле» — мнение; отчёт работает и для моделей без зрения.
  • Решения владельца не принимать молча.Новые цвета и шрифты, отступление от позиции проекта, новый вариант вместо канона — вопрос человеку.
  • Контекст — снимок.Для «как сделать» верить коду, для «как должно выглядеть» — контексту; противоречие — в отчёт.

Если что-то пошло не так

СимптомЧто делать
✗ литерал #… → замени на var(--…)Заменить в указанной строке: переменная уже есть в проекте.
✗ [тема dark] цвет … остался как в основнойЛитерал цвета в новом коде — заменить на переменную из подсказки.
Много ✗ у старых элементовПроверять только новый блок: --selector.
mock build: «✗ AB: похожи»Два варианта с одним паттерном — переделать один по другой строке mock-patterns.md.
