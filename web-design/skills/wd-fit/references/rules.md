## Что читать из контекста

Грузи минимум — контекст устроен так, чтобы каждый файл был самодостаточен:

| Нужно | Откуда |
|---|---|
| Позиция, токены, канон нужных групп, где это в коде | `brief.mjs` — одним выводом, ~2–4 тыс. токенов |
| Как устроен раздел, куда вставить блок, порядок секций | одна схема `compositions/<раздел>.md` (brief называет какую) |
| Готовый блок целиком: шапка, футер, форма, секция | `parts/components.md` |
| Модалка, меню — как открыть и разметка | `parts/overlays.md` |
| Все варианты группы, включая шум | `parts/<группа>.md` — если канона в выжимке не хватило |
| Компоненты, варианты cva/styled, файлы токенов | `source.md` |
| Как выглядело (скриншоты, полный HTML) | `reference/` — только если модель видит изображения и нужно сравнить |

## Сопоставление с каноном

До вёрстки выпиши для каждого нового элемента: «это <группа> → <имя канона> (`id`)». Например:
«кнопка „Выбрать“ → Кнопка основная `1vyvupb`; карточка тарифа → Карточка `h8huo5`; подпись цены → Georgia 14px из типографики».

- Ищи по роли, а не по виду из головы: главное действие — основная кнопка, второстепенное — вторичная/контурная.
- Разметку бери из примера в выжимке (классы, структура), а не пересобирай: тогда и стиль, и исходник совпадут.
- Вариант со статусом «вариант» — допустимая разновидность (например, кнопка-ссылка). Бери его, если контекст тот же.
- «Не разобрано» — разбора не было; бери самые частые и предложи пользователю разметить канон (wd-scan, `parts.mjs`).
- Несколько действий в блоке: одно главное — основная кнопка, остальные — вторичная/контурная. Похожий блок на сайте уже есть
  (карточки фич, тарифы) — повтори его решение, а не придумывай иерархию заново.
- Заголовок блока, подпись, цена — по типографике: найди в схеме раздела соседнюю секцию и возьми тот же тег и размер.
  Таких элементов нет в `parts/`, их проверяет сочетание шрифта в `check.mjs`.

## Позиция проекта

| `stance` | Новый элемент | Шум | Отступление от существующего |
|---|---|---|---|
| `normalize` | только канон | не повторять, даже если рядом он | можно, если ведёт к канону |
| `preserve` | ближайший существующий вариант буквально | повторять можно, если он ближе всего | нельзя без просьбы владельца |
| не задана | самые частые варианты | не повторять | нет; попроси владельца задать позицию |

## Элемент без канона

Переключатель, таблица, степпер, слайдер, тост — в контексте может не быть ничего похожего. Тогда:

1. Поищи в `parts/components.md`, `parts/overlays.md` и `source.md` → «Компоненты» — возможно, он есть в коде или в другом разделе.
2. Нет — собери из токенов: цвета только из палитры, шрифт и размеры из типографики, радиусы и тени из шкал,
   состояния (активное, наведение, фокус) — по аналогии с ближайшей деталью (активный таб — как основная кнопка по цвету).
3. `check.mjs` покажет его как «новый вариант» — это ожидаемо. Остальные нарушения (цвет вне палитры, чужой шрифт) — исправь.
4. В отчёте: «новый элемент X, канона нет, собран из токенов так-то; после слияния стоит переснять контекст и разметить его».

Новый цвет, шрифт или тень — не твоё решение. Спроси; спросить некого — ближайший из палитры, и скажи об этом.

## Спросить некого

Автономный прогон или пользователь не отвечает — не останавливайся и не решай молча:
- просьба противоречит контексту (новый цвет, шрифт, «сделай покрупнее») — сделай по канону, а в отчёте отдельным пунктом:
  что просили, что сделано вместо этого, почему, и что нужно владельцу решить;
- нет канона — собери по разделу «Элемент без канона» и назови элемент новым;
- тексты и данные, которых нет (цены, контакты), — заглушки, явно помеченные в отчёте.

## Код: переменные и компоненты

- Значения — через то, что есть в проекте: CSS-переменные (`var(--color-primary)`), токены темы (Tailwind `bg-brand`,
  `theme.colors.primary`), существующие классы (`.btn .btn-primary`). Литерал `#3b5bdb` в новом коде — нарушение, даже если цвет верный.
- Компоненты — из папок примитивов (`components/ui`, `design-system`): `<Button variant="ghost">`, а не `<button class="…">` с копией классов.
- Новый вариант существующего компонента (например, размер кнопки) — добавь в его определение (cva, styled) рядом с остальными,
  а не стилем на месте; и только если позиция проекта это позволяет.
- Файлы `design-context/` не правь вручную: они генерируются и перезапишутся при пересъёмке.
- Один и тот же файл в двух местах (`source.md` → «Копии файлов», например `src/app.js` и `assets/app.js`) — правь исходник;
  если сборки нет и копия подключена на страницах, поправь обе одинаково и скажи об этом.
- Скрипты проекта, которые ищут элементы по id (`querySelector("#cards").innerHTML = …`), падают на новой странице без этого элемента.
  `check.mjs` покажет `ошибка JS на странице` — почини скрипт (проверка на null), а не подкладывай скрытый пустой элемент.

## Проверка

`check.mjs` открывает страницу тем же Chromium, извлекает основы и детали тем же кодом, что снимал контекст, и сравнивает:

| Строка отчёта | Что значит | Что делать |
|---|---|---|
| `✗ цвет (роль) #x не из палитры` | на странице цвет, которого на сайте нет | взять предложенный (`→`), лучше через переменную |
| `! цвет … почти тот же` | отличие на пару единиц — опечатка или пересчёт | заменить на точный |
| `✗ шрифт X не используется на сайте` | чужое семейство; часто поле или кнопка без `font: inherit` | наследовать шрифт сайта |
| `! сочетание шрифта … не встречается` | размер/вес не из типографики | ближайший размер из подсказки |
| `! радиус / тень не из шкалы` | значение не из шкалы сайта | ближайшее из подсказки |
| `✗ <деталь> — новый вариант` | такой комбинации стилей нет | собрать как ближайший канон (подсказка перечисляет отличия) или объяснить, если канона нет |
| `✗ <деталь> повторяет шум` | вариант помечен в разборе как шум | взять канон из подсказки |
| `✗ литерал … → var(--…)` | в изменённом коде литерал, для которого есть переменная | заменить |
| `✗ цвет … в файле:строка не из палитры` | литерал вне палитры в коде | заменить на цвет палитры через переменную |
| `✓ совпало` | элемент или значение совпало с контекстом | — |

- `--selector` ограничивает проверку новым блоком: старые элементы страницы не мешают и не маскируют проблемы.
- Отступы как шкалу скрипт не проверяет (на реальных сайтах они слишком разнообразны) — их ловит сравнение деталей.
- Состояния (модалка, открытое меню, активный таб) — `--steps`, как в плане контекста: проверяй каждое состояние нового интерактива.
  Мобильный — `--viewport mobile`.
- `ошибка JS на странице` — нарушение: интерактив сайта на этой странице может не работать.
- Скриншот `--shot` — во временную папку, не в репозиторий проекта.
- Пройдено — не значит «красиво»: композицию (порядок, плотность, иерархию) сверяй со схемой раздела, а с изображениями — глазами.

## Свежесть контекста

`brief.mjs` пишет «после съёмки в исходниках N коммитов», если план контекста знает исходники (`src`).
Это не ошибка, но: новые компоненты и токены могли появиться в коде, а в контексте их нет — проверяй `source.md` против кода.
После слияния фичи предложи обновить контекст: страница в план wd-scan и `capture.mjs plan.json --only <id>`, затем разбор новых вариантов.

## Типичные ошибки

- **«Сделал в стиле» без проверки** → `check.mjs` с `--selector` и `--changed`; без него результат не подтверждён.
- **Скопировал вычисленные стили со страницы** (`padding: 10px 18px; background: #3b5bdb`) → классы и переменные проекта.
- **Чуть подправил канон** («радиус поменьше, так красивее») → новый вариант; при `normalize` — нарушение.
- **Читает весь контекст подряд** (все схемы, весь `reference/`) → brief + одна схема; контекст тратится на ненужное.
- **Исправил старые элементы страницы «заодно»** → не в задаче; упомяни в отчёте, не меняй без просьбы.
- **Новый цвет «для акцента»** → спроси владельца; это решение о дизайн-системе, а не о фиче.
