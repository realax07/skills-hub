# wd-forge

Новый дизайн с нуля обычно проваливается двумя способами: агент выдаёт усреднённый «ИИ-дизайн» (Inter, фиолетовый
градиент, одинаковые карточки) или три варианта, которые отличаются оттенком кнопки. wd-forge решает оба:
направления **раздаёт скрипт** из каталогов так, чтобы они были максимально удалены друг от друга по всем осям,
а **проверка в браузере** не пропускает шаблонные приёмы и провалы качества. Пользователь выбирает из трёх
по-настоящему разных вариантов, и выбранный становится дизайн-контекстом для разработки (wd-fit).

## Как выполнять

Для любой модели: шаги по порядку, команды как написано (`<skill>` — папка этого скилла). Не придумывай флаги —
у скриптов есть `--help`. Скрипт упал — смотри «Если что-то не так», не обходи вручную.
Результат — папка `design-forge/` в корне проекта (или где скажет пользователь).

## Процесс

1. **Зависимости.** `node <skill>/scripts/setup.mjs` — проверит запуском и поставит только недостающее. Все строки с ✓ — дальше.

2. **Бриф → `design-forge/PRODUCT.md`.** Шаблон — [assets/PRODUCT.template.md](assets/PRODUCT.template.md). Нужно:
   продукт и предмет, аудитория, главная задача пользователя, **режим поверхности**, ключевые экраны, ограничения
   (бренд-цвет, логотип, язык, тексты). Чего нет в запросе — спроси одним сообщением. **Спросить некого** — прими
   допущения, запиши их в PRODUCT.md с пометкой «допущение» и вынеси в отчёт.
   Режим ([rules.md](references/rules.md#режим-поверхности)): `persuade` — убедить (лендинг, промо, магазин), `operate` — работать
   (приложение, кабинет, админка), `read` — читать (документация, медиа), `experience` — пережить (бренд-история, портфолио).

3. **Раздача направлений.**
   `node <skill>/scripts/deal.mjs --out design-forge --mode <режим> --product "<название>" [--brand "#hex"] [--scheme light|dark]`
   Скрипт выбирает три направления с максимальным расстоянием между ними и пишет в `design-forge/a|b|c/`:
   `tokens.css` (цвета, шрифты, шкала, отступы, радиусы, тени, движение), `base.css` (гигиена: фокус, reduced-motion) и `PLAN.md`.
   Не нравится одно направление — `--reroll <a|b|c>` (остальные не тронет). Не меняй оси руками «под вкус» — разность пропадёт.

4. **План каждого направления — до вёрстки.** Заполни все пропуски в `design-forge/<буква>/PLAN.md`: идея, для кого, каркас
   экранов ASCII, три принципа, **«что тут дефолтное — и что изменено»** (пройди по первому наброску и замени решения,
   взявшиеся «сами собой»), плюсы и минусы. Правила хорошего плана и список шаблонных приёмов — [rules.md](references/rules.md).

5. **Мокапы.** Для каждого направления — экраны из PLAN.md (обычно `index.html` и `detail.html`) в `design-forge/<буква>/`:
   статичный HTML, `<link>` на `tokens.css` и `base.css`, свои стили в `<style>` **только через переменные** токенов.
   Реалистичный текст на языке продукта; никаких выдуманных отзывов, клиентов, цифр и логотипов партнёров; фото — заглушки
   `<div class="ph">` нужных пропорций. Мобильная версия обязательна (медиа-запросы). Скелет экрана — [assets/screen.template.html](assets/screen.template.html).

6. **Проверка.** `node <skill>/scripts/lint.mjs --dir design-forge` — каждый экран на 1440, 768 и 390 px.
   `✗` — ошибка: исправь и запусти снова. `!` — предупреждение: исправь или объясни в PLAN.md. До 3 кругов.
   В конце — «Различие направлений»: `✗` значит два направления слишком похожи — переиграй одно (`deal.mjs --reroll`) и сверстай заново.

7. **Сравнение и утверждение.** `node <skill>/scripts/compare.mjs --dir design-forge` → `design-forge/index.html`:
   три направления рядом (скриншоты десктопа и мобильного, токены, идея, плюсы и минусы, итог проверки).
   Покажи пользователю страницу (путь) и коротко опиши каждое направление текстом. Дальше — его выбор:
   - выбрал — `node <skill>/scripts/approve.mjs --dir design-forge --pick <буква> --run` → `design-context/` (через wd-scan, всё — канон);
   - «взять из B шрифты, из C раскладку» — правь выбранное направление (токены, вёрстку, PLAN.md), снова lint и compare;
   - спросить некого — не утверждай сам: оставь сравнение и в отчёте назови направление, которое рекомендуешь, и почему.

8. **Отчёт.** Где `design-forge/index.html`; по направлению — одна строка (архетип, палитра, шрифты, чем хорош);
   итог проверки; допущения из брифа; что дальше (утверждение → wd-fit для остальных страниц).

## Ключевые правила

- **Три разных, а не три оттенка.** Разность задаёт скрипт; вёрстка должна её сохранить: другой архетип — другая раскладка
  и сценарий, а не та же страница в другом цвете.
- **Смелость по режиму.** Лендинг и бренд-история — смело, с одним запоминающимся приёмом; рабочий интерфейс — сдержанно,
  привычные паттерны, характер в деталях. Игривый шрифт в CRM — ошибка, не смелость.
- **Сначала план, потом код.** Шаблонный дизайн рождается из первых решений «по умолчанию»; раздел «что тут дефолтное» —
  обязательная самопроверка.
- **Только токены.** Цвет, шрифт, отступ — из `tokens.css`. Новое значение — добавь в токены осознанно и отрази в PLAN.md.
- **Без выдумок.** Отзывы, клиенты, цифры, награды — только из брифа. Остальное — нейтральный текст или пометка «пример».
- **Утверждает человек.** Скрипт раздаёт, модель верстает, выбор — за пользователем.
- Подробно: [references/rules.md](references/rules.md). Откуда идеи и лицензии — [references/sources.md](references/sources.md).

## Результат

```
design-forge/
  PRODUCT.md            бриф: продукт, аудитория, задача, режим, экраны, ограничения, допущения
  directions.json       три направления: оси, экраны, расстояния (пишет deal.mjs)
  a/ b/ c/              tokens.css, base.css, PLAN.md, index.html, detail.html (+ другие экраны)
  lint-report.json      итог проверки (lint.mjs)
  index.html            страница сравнения (compare.mjs), _compare/ — скриншоты
  APPROVED.md           что утверждено (approve.mjs)
design-context/         после утверждения: дизайн-контекст по формату wd-scan — дальше работает wd-fit
```

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `deal`: «--mode: одно из …» | укажи режим из шага 2 |
| `deal`: «уже есть — не трогаю» | планы и токены уже заполнены; перезаписать — `--force` (потеряешь правки), одно направление — `--reroll` |
| `lint`: «в PLAN.md не заполнено» | заполни пропуски плана (шаг 4) |
| `lint`: «экран не подключает tokens.css / base.css» | добавь `<link rel="stylesheet" href="tokens.css">` и `base.css` в `<head>` |
| `lint`: «шрифты не из направления» | в стилях — `var(--font-display)` / `var(--font-body)`, не свои семейства |
| `lint`: «шрифт … не загрузился» | нет сети или опечатка в `@import` tokens.css; без сети — допустимо, скажи в отчёте |
| `lint`: «цели нажатия меньше 44px» на мобильном | кнопки, ссылки меню и логотип — `min-height: 44px` (inline-flex) |
| `lint`: «низкий контраст» | текст — `--color-text` или `--color-muted` на `--color-bg`/`--color-surface`; на акценте — `--color-on-accent` |
| `lint`: «Различие направлений ✗» | два направления похожи: `deal.mjs --reroll <буква>`, затем план и вёрстка заново |
| `approve`: «ошибок проверки» | сначала исправь по lint; осознанно утвердить с ошибками — `--force` |
| `approve --run`: «не нашёл wd-scan» | `--wd-scan <папка скилла wd-scan>` или выполни команды, которые печатает approve без `--run` |

## Пример

**Запрос:** «Нужен сайт для нашей обжарочной „Зерно“, покажи пару вариантов дизайна».
**Ход:** бриф (режим persuade, экраны: главная и подписка) → deal: A «Сначала демо» (сланец, DM Serif, острые углы),
B «Бенто-витрина» (тёмное бордо и золото, Instrument Serif), C «Редакционный манифест» (небо и солнце, Fraunces, воздух) →
планы → 6 экранов → lint: логотип 39px на мобильном → исправлено, 0 ошибок, направления различаются → compare → пользователь
выбрал C → approve --run → `design-context/` с каноном → дальше wd-fit.

- [examples/02-saas-dashboard-bad-good.md](examples/02-saas-dashboard-bad-good.md) — рабочий интерфейс: три оттенка одного и шаблон против трёх направлений
