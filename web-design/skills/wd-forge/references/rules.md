## Режим поверхности

От режима зависит, насколько смело можно. Определи по главной задаче пользователя, не по типу компании.

| Режим | Что | Смелость | deal.mjs ограничивает |
|---|---|---|---|
| `persuade` | лендинг, промо, магазин, страница продукта | смело: позиция, характер, один запоминающийся приём | — |
| `operate` | приложение, кабинет, админка, дашборд | сдержанно: привычные паттерны, плотность, скорость | плотность compact/regular, движение still/subtle, без игривых и плакатных шрифтов |
| `read` | документация, медиа, база знаний | текст главный: колонка, ритм, типографика | плотность regular/airy, движение still/subtle |
| `experience` | бренд-история, портфолио, событие | максимально смело: сцена, движение, неожиданность | движение orchestrated/expressive |

Сайт компании с кабинетом — два режима: лендинг (`persuade`) и кабинет (`operate`) — две отдельные раздачи в разных папках.

## Оси направления

deal.mjs раздаёт по шести осям и выбирает тройку с максимальным **минимальным** расстоянием между любыми двумя:

| Ось | Значения | Что меняет в мокапе |
|---|---|---|
| UX-архетип | по режиму: история-скролл, бенто, манифест, сначала демо, каталог; сайдбар, командный центр, список-деталь, доска, мастер… | раскладку, навигацию, сценарий, что на первом экране |
| Палитра | 28 палитр: светлые и тёмные, тёплые и холодные, спокойные и яркие | фон, текст, акцент — и настроение |
| Типографика | 31 пара Google Fonts (20 с кириллицей): антиква, гротеск, моно, акцидентные | характер; заголовки несут личность |
| Форма | острая, мягкая, округлая | радиусы и тени |
| Плотность | плотная, обычная, воздушная | шкала отступов и размеров, колонка текста |
| Движение | статичное, сдержанное, оркестрованное, выразительное | переходы и один момент появления |

Архетип — главная ось: два направления с одним архетипом в разных цветах — это один вариант. Поэтому в вёрстке архетип
должен быть **виден**: у «сайдбара» — сайдбар, у «манифеста» — огромная типографика и колонки, у «демо» — интерактив над сгибом.

## Язык, отрасль, темы

deal.mjs учитывает их сам — по `--product` и `PRODUCT.md`; флаги нужны, только если он ошибся.

- **Язык.** Кириллица в брифе — только шрифтовые пары с кириллицей у заголовков и текста (флаг `cyr` в каталоге
  проверен по Google Fonts). Иначе русские заголовки упадут в запасной Georgia, и характер направления пропадёт.
- **Отрасль** (`industries` в `system.json`): ключевые слова брифа → правила в PLAN.md («Отраслевые правила»)
  и ограничения: спокойные палитры для медицины и госсервисов, без игривых шрифтов в финансах и т.п. Правила — это
  требования к вёрстке: табличные цифры в финансах, запись с первого экрана у клиники, копирование кода у девтулов.
- **Темы.** `operate` и `read` по умолчанию получают две темы: основная (по палитре) и вторая, выведенная из неё
  с проверкой контраста (`:root[data-theme="dark|light"]` в tokens.css). Вёрстка одна — только переменные; lint проверяет
  обе. Лендингу вторая тема обычно не нужна; нужна — `--themes both`.
- **Статусные цвета и ссылка** — в токенах каждой темы: `--color-success|warning|danger` (+ `-soft` для подложек,
  `--color-on-danger`), `--color-link` (акцент, если он читается как текст, иначе тот же тон контрастнее). Свои
  «зелёный для успеха» не вводи.

## Хороший план

PLAN.md заполняется до вёрстки, потому что шаблонный дизайн рождается из первых решений «по умолчанию».

- **Идея** — одна-две фразы: как направление отвечает на бриф и чем оно не похоже на два других.
- **Сценарий** — кто приходит и что делает по экранам.
- **Каркас** — ASCII: зоны и их порядок, что крупно, что мелко. По опоре архетипа, но под продукт.
- **Принципы** — три правила, по которым принимаются мелкие решения («каждая плитка — один сорт или один факт»).
- **«Что тут дефолтное — и что изменено»** — пройди по первому наброску: центрированный герой, три карточки преимуществ,
  eyebrow над заголовком, градиент, иконки в плитках, «→» в ссылках — что из этого появилось само и на что заменено.
- **Плюсы и минусы** — честно: пользователь выбирает по ним.

## Шаблонный «ИИ-дизайн»

Признаки, по которым сайт узнаётся как сгенерированный. lint.mjs ловит большую часть на отрисованной странице.

| Признак | Почему плохо | Вместо |
|---|---|---|
| Inter / Roboto / Arial / системный шрифт основным | дефолт — нет личности | пара из направления |
| Фиолетово-синий градиент | главный признак шаблонного SaaS | палитра направления; градиент — только если он идея |
| Кремовый фон + терракота; почти чёрный + кислотный акцент | узнаваемые кластеры | палитры каталога их обходят — не возвращай руками |
| Одинаковые скруглённые карточки с мягкой тенью в каждой секции | «конструктор» | разная форма блоков по смыслу: список, таблица, линия, плитки разного веса |
| Карточка внутри карточки | шум | один уровень контейнера |
| Квадратная плитка с иконкой над каждым заголовком | шаблон «фичи» | иконка — только если она несёт смысл; иначе типографика |
| Мелкие заглавные с разрядкой (eyebrow) над каждым заголовком | шаблон | один раз, если это часть системы |
| Эмодзи вместо иконок; «→» в каждой ссылке | дёшево | SVG-иконки или текст |
| Fade-up на каждой секции | движение без смысла | один оркестрованный момент |
| Всё по центру | нет композиции | выравнивание по сетке, асимметрия |
| Выдуманные отзывы, клиенты, цифры, награды, обещания и условия (сроки, гарантии, «без штрафа») | ложь и обязательства, которых бизнес не давал | только данные из брифа; иначе — пометка «пример» |

## Пол качества

Не дизайн, а гигиена — проверяется на 1440, 768 и 390 px:

- нет горизонтального скролла;
- контраст текста ≥ 4.5 (крупный ≥ 3); палитры каталога его соблюдают, если текст на `--color-text`/`--color-muted`;
- цели нажатия ≥ 24px, на мобильном ≥ 44px по **обеим** сторонам (ссылки внутри текста не считаются); нативные чекбоксы — явный размер или крупный `<label>`;
- видимый `:focus-visible` (даёт base.css); анимации — с `@media (prefers-reduced-motion)` (даёт base.css);
- анимируй `transform` и `opacity`, не `transition: all`;
- картинки и заглушки — с размерами или `aspect-ratio` (нет сдвига вёрстки);
- состояния, которые есть в сценарии (пусто, ошибка, загрузка), — нарисованы хотя бы на одном экране для `operate`.

## Мокапы

- Статичный HTML без сборки и фреймворков: открывается двойным кликом, снимается wd-scan.
- `<link>` на `tokens.css` и `base.css`, свои стили — в `<style>` через переменные. Новое значение — в токены, а не литералом.
- Экраны связаны ссылками (логотип → главная, кнопки → второй экран): так страница сравнения и съёмка видят сценарий.
- Текст — на языке продукта, конкретный («Обжарка по понедельникам»), без lorem ipsum. Цифры и отзывы — только из брифа.
- Фото — заглушки `.ph` нужных пропорций с `aria-label` «что на фото». Логотип — текстовый, если файла нет.
- Мобильная версия — медиа-запросы в каждом экране, проверь на 390 px.
- Объём: 2 экрана на направление по умолчанию; больше — только если просит пользователь (×3 работы).

## UI-кит

`kit.html` — третий обязательный экран. Мокапы показывают сценарий, а кит — все детали и состояния, из которых потом
собирается продукт. После утверждения wd-scan снимает кит, детали с `data-part` становятся каноном с именами
(«Кнопка основная», «Поле с ошибкой»), и wd-fit делает новые страницы из них. Чего нет в ките — того нет в каноне.

- Заготовка из `assets/kit.template.html` нейтральна: **адаптируй** её под направление — форма кнопок (заливка, контур,
  регистр, вес), поля (рамка или подчёркивание), метки, таблица, плотность. Это раздел «kit.html» в PLAN.md.
- Имена `data-part` не меняй и не удаляй: lint требует обязательные (`kit` в `system.json`; у `operate` — ещё таблица,
  вкладки, загрузка, диалог, опасная кнопка, список выбора).
- Экраны собирай **теми же классами**, что в ките: иначе в каноне окажется по два варианта каждой кнопки.
- Новая деталь, нужная продукту (степпер, календарь), — добавь в кит со своим `data-part`.

## Проверка

`lint.mjs` открывает каждый экран на трёх ширинах. Ошибки (`✗`) блокируют утверждение, предупреждения (`!`) — нет.

| Правило | Уровень | Что делать |
|---|---|---|
| `plan` — не заполнен PLAN.md | ✗ | шаг 4 |
| `kit-missing` — в kit.html нет обязательной детали | ✗ | верни её из `assets/kit.template.html`, имя `data-part` — как в списке |
| `off-kit` — кнопка, поле или метка на экране не совпадает ни с одной деталью кита | ✗ | возьми класс из kit.html; деталь продукта (слот расписания, чип фильтра) — добавь в кит со своим `data-part` |
| PLAN.md: раздел «kit.html» короткий | ✗ | опиши, что в заготовке кита изменено под направление — кнопки, поля, метки, таблица |
| `no-tokens` / `no-base` | ✗ | подключи файлы в `<head>` |
| `h-scroll` | ✗ | найди элемент шире окна (в примерах), добавь `min-width: 0`, перенос, медиа-запрос |
| `contrast` | ✗ | цвета текста из токенов, на акценте — `--color-on-accent` |
| `targets` | ✗ на мобильном, ! на десктопе | `min-height: 44px`, `inline-flex` |
| `focus`, `reduced-motion` | ✗ | подключи base.css |
| `default-font`, `off-direction-font` | ✗ | `var(--font-display)`, `var(--font-body)` |
| `purple-gradient` | ✗ | убери градиент или сделай его идеей направления в палитре |
| `js-error` | ✗ | почини скрипт мокапа |
| `nested-cards`, `icon-tiles`, `eyebrows`, `emoji-icons`, `arrow-links`, `same-animation`, `all-centered` | ! | замени по таблице «Шаблонный ИИ-дизайн» или объясни в PLAN.md, почему это идея |
| `off-tokens` | ! | цвет вне токенов: добавь в tokens.css осознанно или замени на переменную |
| `font-not-loaded` | ! | нет сети или опечатка в `@import`; без сети — допустимо |
| `transition-all`, `img-size` | ! | по таблице «Пол качества» |
| Различие `✗` | ✗ | два направления похожи (шрифт, схема и акцент, раскладка): `deal.mjs --reroll <буква>` |

Пройдено — не значит «красиво». Модель с изображениями смотрит скриншоты на странице сравнения; без изображений —
сверяет вёрстку с PLAN.md: виден ли архетип, соблюдены ли принципы.

## Утверждение и смешивание

- Выбор одного — `approve.mjs --pick <буква> --run`: план wd-scan (экраны и кит направления, вторая тема, позиция
  «к канону»), съёмка, детали кита — канон с именами из `data-part`, остальные — канон без имени. Дальше новые страницы делает wd-fit по `design-context/`.
- «Взять из B шрифты, из C раскладку» — не новое направление, а правка выбранного: замени в `tokens.css` нужные переменные
  (шрифты — вместе с `@import`), поправь PLAN.md, lint и compare заново, затем утверждение.
- Утверждать с ошибками проверки — только осознанно (`--force`) и с пометкой в отчёте.

## Спросить некого

- Бриф: допущения с пометкой в PRODUCT.md и в отчёте (режим, экраны, тон).
- Бренд-цвета нет — раздача без `--brand`; не придумывай «фирменный» цвет.
- Утверждение — решение человека: не запускай approve сам; в отчёте — рекомендация и почему.

## Типичные ошибки

- **Три оттенка одного** → разность задаёт deal.mjs; не сводить направления к одной раскладке в вёрстке.
- **Вёрстка без плана** → шаблонные решения «по умолчанию»; PLAN.md до кода.
- **Литералы в стилях** → lint ловит цвета вне токенов; всё через переменные.
- **Красивый десктоп, сломанный мобильный** → проверка на 390 px обязательна.
- **Выдуманные «нам доверяют 500 компаний»** → только данные из брифа.
- **Модель утвердила сама** → выбор за пользователем.
