## Куда класть результат

Пользователь указал путь — используй его. Иначе:

1. **В репозитории сайта** — `design-context/` в корне (в монорепо — рядом с фронтенд-приложением: `apps/web/design-context/`).
   `plan.json` — туда же. Папка уже есть и создана не этим скиллом (нет `reference/manifest.json` с
   `"generator": "wd-scan"`) — спроси, прежде чем писать.
2. **Не в репозитории сайта** — спроси, предложив `./<домен>-design-context/`.
   Есть похожая папка, созданная людьми (`design/`, `docs/design/`), — не пиши в неё и не смешивай: клади в `design-context/`
   рядом и упомяни её в отчёте (возможно, там правила, которые стоит сослать из `GUIDE.md`).
3. Сообщи путь и предложи `.gitignore` для `design-context/reference/`: там скриншоты и кэш (десятки МБ).
   Слой для агента (`GUIDE.md`, `foundations.md`, `parts/`, `compositions/`, `assets/`) лёгкий — его коммитят.

Почему одно место: агент в любом репозитории знает, где искать дизайн, а указатель в AGENTS.md ведёт туда же.
Следующие скиллы подготовки проекта (архитектура, API, домен) кладут свои папки рядом по тому же принципу.

## Позиция проекта

Извлечение описывает, **что есть**, а не что правильно. На легаси будет 14 оттенков серого и 20 «вариантов» кнопки;
на дизайнерском сайте — тоже десятки вариантов, но осмысленных. Что из этого агенту размножать — решает владелец.

Спроси пользователя и запиши в план `stance`:

| `stance` | Когда | Что агент делает с новым |
|---|---|---|
| `preserve` | легаси, строгий регламент, «нельзя ничего менять визуально» | повторяет ближайший существующий вариант буквально, даже неидеальный |
| `normalize` | дизайн развивается, хочется навести порядок | использует только канон из разбора; шум и легаси не размножает |

Не спросил — в `GUIDE.md` останется пометка «не задана», и агент возьмёт самые частые варианты. Это хуже, чем решение человека.

## Указатель в контексте проекта

Контекст бесполезен, если агент о нём не знает. Файл инструкций проекта (AGENTS.md, CLAUDE.md…) агент читает
в каждой сессии — туда вписывается короткий блок: какие вопросы решает дизайн-контекст и путь до `GUIDE.md`.

1. Кандидаты: `node scripts/link-context.mjs --suggest --root <корень репо>`.
2. **Спроси пользователя** — это его файл, который читают все агенты проекта. Рекомендация:
   - есть `AGENTS.md` — его (Codex, OpenCode, Qwen Code, Hermes и др.; `CLAUDE.md` с `@AGENTS.md` подхватит сам);
   - есть только `CLAUDE.md` / `GEMINI.md` / другой — его; несколько независимых — все (`context` — массив);
   - нет ни одного — создать `AGENTS.md`;
   - «никуда» — тоже ответ: дай путь до `GUIDE.md` в отчёте.
3. `"context": "../AGENTS.md"` в плане (путь от папки плана) — каждый прогон обновит блок, без изменений файл не тронет.

Блок между `<!-- wd-scan:start -->` и `<!-- wd-scan:end -->`; текст вне меток не меняется.
Свои правила про дизайн пиши вне меток. Убрать — `link-context.mjs <out> --into <файл> --remove`.

## Что снимать

Чек-лист охвата для плана. Каждая страница и состояние — это и схема раздела, и источник деталей.

**Страницы (`pages`)** — каждый уникальный шаблон: главная, лендинги, список/каталог, карточка/деталь, статья,
формы, кабинет/дашборд, настройки, 404, пустые состояния, логин. Однотипных — 1–2 представителя.
Все уровни вложенности (`/docs/installation/framework-guides/laravel/vite`) — это разные шаблоны.

**Состояния** — страница со `steps` (`home--login-open`, `catalog--filters-open`): деталей в открытых модалках и меню
иначе не найти, а схема показывает, как оверлей лежит поверх раздела.

**Компоненты (`components`)** — значимые блоки, которые агент будет переиспользовать целиком:

| Группа | Что |
|---|---|
| `layout` | header, nav, footer, sidebar, breadcrumbs |
| `sections` | hero, фичи, цены, отзывы, CTA, FAQ |
| `content` | карточки, списки, таблицы, медиа |
| `forms` | формы целиком, состояния ошибок |
| `navigation` | табы, пагинация, степперы |
| `feedback` | алерты, тосты, лоадеры, скелетоны, пустые состояния |

Мелкие элементы (кнопки, поля, ссылки, бейджи) перечислять в плане не нужно — их находит извлечение на всех страницах.
Компоненты из плана в схемах страниц заменяются ссылкой на `parts/components.md` — это экономит контекст.

**Модалки (`modals`)** — окна, дроверы, дропдауны, поповеры, тултипы, мобильное меню, cookie-баннер.

**Вьюпорты:** desktop всегда; mobile (390×844, `isMobile: true`) для страниц и всего, что перестраивается.
HTML мобильной страницы с той же разметкой не дублируется — эталон второго вьюпорта хранится скриншотом.

## Разбор деталей

После съёмки `parts/*.md` и `reference/parts.html` содержат **все** найденные варианты — это сырьё. Разбор превращает его в норму.

1. Посмотри варианты: `node scripts/parts.mjs <out> --group buttons` (текст: частота, страницы, стиль, классы, исходник)
   или `reference/parts.html` (вырезки — если модель видит изображения).
2. Для каждой группы реши:
   - **канон** — роль понятна (основная, второстепенная, призрачная, опасная кнопка…), встречается на многих страницах;
   - **вариант** — допустимая разновидность канона (размер, контекст: кнопка в тёмной секции);
   - **шум** — случайность, легаси, ошибка вёрстки (ссылка-кнопка с подчёркиванием), не та категория (пункт меню, строка аккордеона, редактор кода в «полях»).
3. Дай канону и вариантам имена: `"name": "Кнопка основная"`. Имя увидит агент-потребитель.
4. Пометь: `node scripts/parts.mjs <out> --set <id>=canon:"Кнопка основная" <id>=noise …`, хвост группы — `--group buttons --rest noise`.
   Скрипт пишет `parts` в план и пересобирает слой (`capture.mjs --rebuild`) без съёмки. Править JSON руками тоже можно.

Ориентиры: на чистой системе канон — 2–5 кнопок, 1–3 поля, 2–4 ссылки. Если «канонов» выходит 15 — либо это шум,
либо в системе нет порядка; тогда спроси пользователя по вырезкам, не угадывай. Для `stance: preserve` статусы всё равно
полезны: агенту проще повторить «ближайший», когда известно, какие варианты главные.

## Разделы и схемы

- `path` страницы задаёт раздел: `/blog/first-post` → `compositions/blog--first-post.md`, эталон — `reference/blog/first-post/`.
  Задавай реальные пути сайта.
- Схема — сжатая разметка: svg без путей, текст обрезан, повторы свёрнуты в «…повтор ×N», скрытое не выводится,
  компоненты из плана — ссылками. Ориентир — 1–30 тыс. токенов на раздел; больше — значит, много контента (документация, статьи).
- Общие компоненты (шапка, футер, общие модалки) снимай на главной — в схемах всех разделов они станут ссылками.

## Исходники

Браузер отвечает «что видит пользователь», код — «где это задано и что переиспользовать». Код необязателен,
но если он доступен — всегда давай `"src"` в плане: агент-потребитель будет менять именно код.

**Что указать в `src`** (путь или массив путей от папки плана):
- статический сайт без сборки — его папку целиком (`"../site"`): там и есть исходники; копии файлов учитываются один раз;
- папку фронтенда: `"../src"`, `"../apps/web/src"`; в монорепо — ещё пакет UI: `["../apps/web", "../packages/ui"]`;
- не указывай `node_modules`, сборку (`dist`, `.next`) и весь монорепо целиком — они пропускаются или дают шум;
- конфиги рядом с `package.json` (tailwind, panda, `components.json` и т.п.) подхватываются сами, даже если `src` — подпапка.

**Что получится** (`source.md`, пересобирается при каждом `capture`, включая `--rebuild`):

| Раздел | Откуда |
|---|---|
| Стек | `package.json` в `src` и выше до корня репо: фреймворк, стили, UI-библиотеки, варианты (cva, tailwind-variants), анимации, иконки, шрифты |
| Токены | определения CSS-переменных с контекстом (`:root`, `.dark`, `[data-theme]`), отметка «на сайте»; `$scss`/`@less` переменные |
| Темы и конфиги | `tailwind.config.*` (`theme`), Tailwind 4 `@theme`, `createTheme`/`extendTheme`/`createStitches`/vanilla-extract, JSON-токены |
| Варианты | `cva(`, `tv(`, `styled.x`, рецепты Panda / vanilla-extract — где определены варианты компонентов |
| Компоненты | экспортируемые компоненты по папкам; `ui/`, `primitives/`, `design-system/` помечены как примитивы |
| Движение, иконки, шрифты | `@keyframes`, импорты framer-motion/gsap/lottie…, иконочные библиотеки с именами иконок, `next/font`, `@font-face` |

**Деталь → файл.** Для каждой найденной детали ищется исходник: CSS-модуль (`Button_primary__x1y2z` →
`Button.module.css .primary`), класс из CSS проекта (`.btn-primary`), строка классов в коде с теми же утилитами
(Tailwind: `cva("inline-flex rounded-lg …")`). Ссылки — в `parts/*.md` («исходник») и в `parts.mjs --group`.
Нет ссылки — разметка собирается динамически, классы сгенерированы (CSS-in-JS) или деталь из сторонней библиотеки.

**Расхождения.** Переменная в коде есть, а на сайте не применяется («на сайте» пусто) — мёртвый токен или другая тема.
Цвет на сайте литералом, а в коде есть переменная с тем же значением — повод при `normalize` использовать переменную.
Значения различаются — верь браузеру и отметь в отчёте.

Только чтение: скилл не запускает сборку и не ставит зависимости проекта; секреты из `.env` не читаются (файлы `.*` пропускаются).

## Именование и группы

- `id` — kebab-case, уникален: `pricing-card`, `login`, `home--login-open`; состояния — через `--`.
- `title` — по-человечески, на языке сайта: «Окно входа», «Карточка тарифа».
- `notes` — что это, где встречается, как открывается: «Открывается по „Войти“ в шапке; закрывается Esc».

## Селекторы

Приоритет: `#id` → `[data-testid]`/`[data-test]`/`[data-qa]` → роль/ARIA (`[role=dialog]`, `[aria-label="Меню"]`)
→ семантичные классы → структурный путь. Избегай хэшей CSS-модулей и CSS-in-JS (`.sc-bdVaJa`, `._abc123`),
id, которые фреймворк генерирует (`#headlessui-menu-button-_R_…`, `#radix-:r1:`), текста, который меняется.
Хэшированный класс можно матчить частично: `[class*="Button_root"]`.

## Медиа: дизайн или контент

Контекст хранит дизайн, а не контент. Фото статей и товаров, скриншоты продукта, видео — контент: в эталоне они
заменяются заглушками тех же пропорций (`data-mockup-placeholder`, исходник в `data-mockup-src`).
Логотипы, иконки, фоны, шрифты, фоновые видео — дизайн: скачиваются, иконки и логотипы попадают в `assets/`.
Классификация и переопределение — [plan-format.md](plan-format.md#media).

## Модалки и состояния

- Открывай реальным действием (`click`, `hover`, `focus`, `press`), затем `waitFor`.
- Модалку с затемнением — двумя элементами: сам диалог в `modals` и страница в этом состоянии (`pages` со `steps`).
  В `modals.selector` — окно (`[role=dialog]`, `.modal`), не подложка: снимок полупрозрачной подложки без страницы под ней
  всегда расходится с оригиналом (`verify` 5–10%).
- Окна и меню из `modals` не попадают в группу «Карточки» автоматически; если что-то похожее туда попало — `noise`.
- Не открыть без бэкенда — снимай со стейджа или отметь пропуск; подмена DOM через `eval` — только с согласия пользователя.
- Анимации на время снимка эталона отключаются, но **извлечение движения** читает переходы и `@keyframes` до отключения.

## Приватность и доступ

- Никаких реальных персональных данных: тестовые аккаунты, выдуманные значения в формах.
- Пароли и токены не вводи и не клади в план. Для страниц за логином — `storageState` от пользователя
  (`npx playwright codegen --save-storage=auth.json <url>`, логин делает он сам); файл сессии — в `.gitignore`.
- Чужие сайты — только по просьбе пользователя и для его задачи.

## Ограничения и обходы

| Симптом | Причина | Что делать |
|---|---|---|
| Деталей в группе слишком много | шум, легаси или эвристика захватила лишнее (пункты меню как кнопки) | это нормально — разбор (`status: noise`) |
| Нужной детали нет среди найденных | она видна только после действия или ниже 20 000 элементов на странице | добавь состояние со `steps`, где она видна; или компонент в план |
| Деталь без строки «исходник» | классы собираются в рантайме, CSS-in-JS, сторонняя библиотека | норма; ищи компонент по тексту в `source.md` → «Компоненты» |
| Нет вырезки у варианта | элемент перекрыт, вне экрана или исчез к моменту снимка | ориентируйся на разметку и стиль в `parts/*.md` |
| В движении «нет признаков JS», а сайт анимирован | анимация на canvas/WebGL или запускается по скроллу | опиши словами в `notes` компонента; при необходимости — скриншоты состояний |
| Цвет без имени переменной | сайт задаёт его литералом, не через `:root` | так и есть; при `normalize` — повод завести переменную |
| В схеме раздела много текста | раздел — документация или статьи | норма; агенту обычно нужна структура в начале схемы |
| `verify`: «картинка/CSS/шрифт не загрузился» | ассет не скачался (CORS, авторизация, 404) | `reference/capture-log.json` → warnings; `storageState` или другое окружение |
| `verify` чуть выше порога на мелком тексте | субпиксельная растеризация | открой оба изображения; если одинаково — объясни в отчёте |
| Компонент «съехал» в эталоне | стили зависят от соседей | сними родителя целиком или `fitSize: false` |
| Предупреждение «нет `<meta name="viewport">`» | сайт не адаптирован: на телефоне рисуется десктоп ~980px | не ошибка; записано в `foundations.md` («Особенности вёрстки») — скажи в отчёте |
| У детали «⚠ шрифт не из основных» | поле или кнопка без `font: inherit` — браузерный шрифт | при `preserve` так и повторять; при `normalize` — повод исправить |
| «исходник: те же классы в коде (возможно, другой экземпляр)» | совпали только классы, текст другой | проверь глазами перед правкой файла |
| `iframe`, closed shadow DOM пустые | не сериализуются | опиши в `notes`; open shadow DOM поддержан |
| Шаг падает по таймауту | селектор не тот, перекрыт, нужен скролл | проверь в `discovery.json`; `scroll`; баннеры — `defaults.hide` |

## Типичные ошибки

- **Размножить шум** → агент делает 21-й вариант кнопки. Разбор и позиция проекта обязательны.
- **Только детали, без композиций** → правильные кубики, собранные пусто и усреднённо. Снимай каждый шаблон страницы.
- **Скачать HTML через curl** → на SPA пустой `<div id="root">`. Только через браузер.
- **Не открыть модалки и меню** → самые нужные детали не найдены.
- **Хэш-классы и сгенерированные id в селекторах** → план не переиграть.
- **Коммитить `reference/`** → десятки мегабайт скриншотов в репозитории.
