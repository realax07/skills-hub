## Стадия 1. Реверс-инжиниринг существующей веб-системы

**Цель.** Из работающей системы (сайт, исходники, сборка, инфраструктура) собрать контекст,
по которому код-агенты смогут дальше её разрабатывать: понимать, как она устроена, и менять её, не ломая.

**Принцип:** один скилл на один аспект системы; скиллы одного аспекта — набор в своей теме с общим префиксом
(дизайн — тема [web-design](web-design/), набор `wd-*`).
Каждый скилл кладёт компактный слой контекста в свою папку в корне репозитория проекта
и вписывает указатель на него в файл инструкций проекта (AGENTS.md, CLAUDE.md…).

### 3.1 — sa-scan (сделано 2026-11-19)

Решено:
- **Формат — OpenSpec 2.x** (`openspec/specs/<cap>/spec.md`, `config.yaml` вместо `project.md`); заголовки и SHALL/MUST, WHEN/THEN — по-английски, текст — на языке проекта
  (так же, как делает `openspec init --language ru`; сверено на реальных русских спеках, проходящих `--strict`).
- **Сознательно расходимся с советом OpenSpec** «не описывать систему целиком заранее»: для перевода на агентов нужна карта до первой задачи.
  Устаревание закрываем трассировкой «требование → код», проверкой покрытия входов и режимом «обновить после изменений кода».
- **Спека — «как есть», с багами.** Расхождение кода с PRD — всегда вопрос с допущением и пометкой `(допущение: Q-…)`.
  Ответ «в коде ошибка» не переписывает основную спеку, а рождает предложение изменения в `openspec/changes/` — это и есть вход в SDD.
- **Вопросы — в файл всегда** (`system-context/QUESTIONS.md`, чек-лист собирает скрипт), в чат — 5–7 главных; человек отвечает в файле или в чате.
- **Детерминированное — скриптами** (Python stdlib): опись (`inventory.py`, ~15 стеков эвристиками, префиксы роутеров Express, SDK по импортам),
  план (`plan.py`), вопросы (`questions.py`), проверка (`check.py`: покрытие, формат спек и дельт, трассировка, пометки, интеграции, указатель; `openspec validate`, если CLI есть).

Дальше (⏳):
- **3.2 sa-change** (стадия 2): доработка по спекам — предложение изменения `openspec/changes/` с опорой на `system-context/`, реализация, обновление трассировки.
- **3.3 sa-drift**: периодическая сверка спек с кодом — новые и исчезнувшие входы, изменения в обход `changes/`, требования без теста.
- Прогон evals на слабой модели; проверка формата на живом CLI OpenSpec (здесь его не было — проверено своим разбором и на реальных спеках).

**Принцип:** скилл стадии 2 потребляет папку контекста скилла стадии 1 того же набора
и проверяет изменение измеримо (скриптом), а не на глаз.

### 2.2 — мокапы доработки на утверждение (сделано 2026-11-18)

Идея: по готовому `design-context/` генерировать **дизайн новой доработки** до реализации — три варианта на выбор,
затем утверждённый реализуется в коде как сейчас (2.1). Не путать с 2.3: там дизайн всего продукта с нуля.

Черновик процесса (новый первый шаг wd-fit):
1. Выжимка контекста (`brief.mjs`).
2. Три варианта мокапа — **в контексте реальной страницы** (схема раздела из эталона с вставленным блоком, а не блок на пустом листе).
   Варианты должны реально различаться: UX/сценарий (тарифы: три карточки / таблица сравнения / переключатель с выделенной карточкой),
   композиция и плотность, использование палитры (акценты, тёмная/светлая секция, роль основного цвета).
3. Скрипт проверки различий — чтобы не вышло три оттенка одного (иначе слабая модель так и сделает).
4. Каждый мокап — через `check.mjs`.
5. Страница сравнения трёх вариантов рядом: описание, плюсы и минусы, итог проверки → пользователь выбирает.
6. Реализация выбранного в коде и финальная проверка.

Сделано (2026-11-18) — шаг 4а wd-fit, **необязательный**: включается, когда просят варианты или доработка крупная и есть кого спросить;
мелкие правки — сразу в код (три варианта утраивают работу). `mock.mjs new` — папка, PLAN.md, заготовки фрагментов, блоки страницы
для места вставки; агент верстает только блок; `mock.mjs build` вставляет его в копию страницы из эталона (`reference/`),
прогоняет `check.mjs` во всех темах, меряет различие (структура обязана различаться у каждой пары, палитра — хотя бы у одного),
пишет `index.html` сравнения. Паттерны «тип доработки → три подхода» — `references/mock-patterns.md` (опора для слабых моделей).
Выбор — за человеком; спросить некого — рекомендация без реализации.

Попутно (2026-11-18) — **темы в wd-scan** (был пробел: снималась только основная тема, переменные из
`@media (prefers-color-scheme: dark)` даже затирали светлые значения): поле `themes` в плане, проход по каждой теме,
раздел «Темы» в `foundations.md`, блок темы в `tokens.css`; wd-fit проверяет каждую тему и ловит литералы светлой темы.
Совет по `.gitignore` сужен до скриншотов эталона: HTML-копии страниц нужны мокапам.

Решено (2026-11-18): **генерация по готовым токенам — всегда wd-fit**: варианты различаются UX, композицией и использованием
существующей палитры, `check.mjs` строгий. Новая система (новые цвета, шрифты, характер) — это wd-forge (2.3), а не wd-fit.

### 2.3 — wd-forge: исследование и план (2026-11-18)

**Что взято у топовых решений** (идеи пересказаны своими словами; при заимствовании текста или данных — уведомление о лицензии):

| Источник | Лицензия | Что берём |
|---|---|---|
| [frontend-design](https://github.com/anthropics/skills/tree/main/skills/frontend-design) (Anthropic) | Apache-2.0 | Сначала план, потом код: предмет, аудитория, главная задача → компактная система токенов (4–6 цветов, роли шрифтов, ASCII-каркас) → самопроверка «не дефолт ли это» → код. Список «кластеров ИИ-дизайна», которых избегать. Одно оркестрованное движение вместо fade-up на каждой секции. Пол качества: адаптив, фокус, reduced-motion, контраст |
| [Impeccable](https://github.com/pbakaus/impeccable) (Paul Bakaus) | Apache-2.0 | Режим поверхности: Persuade / Operate / Read / Experience — смелость по режиму (лендинг смелый, рабочий интерфейс сдержанный). PRODUCT.md как вход. Детерминированный детектор «тел» ИИ-дизайна на отрисованной странице. Генерация вариантов элемента. Телеметрию и хуки не берём |
| [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) | MIT | Выбор по данным, а не по вдохновению: каталоги стилей, палитр, шрифтовых пар, отраслевых правил и анти-паттернов + скрипт поиска (stdlib). Чек-лист перед сдачей. Хорошо для слабых моделей |
| [taste-skill](https://github.com/Leonxlnx/taste-skill) | MIT | «Раздача» направлений скриптом из каталогов с историей (раскладка героя, палитра под отрасль, шрифтовая пара, радиус); проверка правил в настоящем Chrome с «финишными воротами» до 3 кругов; не выдумывать отзывы, клиентов, цифры |
| [Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines) (Vercel) | MIT | Пол качества как проверяемые правила: клавиатура и `:focus-visible`, цели ≥24/44px, `prefers-reduced-motion`, анимировать только transform/opacity, все состояния (пусто, ошибка, загрузка), размеры картинок, многослойные тени, вложенные радиусы |

Никто из них не делает того, что нужно нам: **три диаметрально разных направления на утверждение** и выход в формате,
который берёт следующий скилл. Это и есть отличие wd-forge.

**План процесса wd-forge:**
1. **Бриф → `PRODUCT.md`**: продукт, аудитория, главная задача, режим поверхности, ключевые экраны (по умолчанию 2: главный и один рабочий), ограничения (бренд-цвет, логотип). Спросить некого — допущения в отчёт.
2. **Раздача трёх направлений скриптом** (`deal.mjs`): точки в пространстве осей — UX-архетип и раскладка (история-скролл / плотный каталог / конфигуратор / редакционная…),
   палитра (тон, светлая/тёмная, контраст), типографика (антиква / гротеск / моно / акцидентный), форма (радиус), плотность, характер движения.
   Скрипт выбирает три **максимально удалённые** точки с учётом режима и отрасли и отсекает «кластеры ИИ-дизайна». Детерминированно — слабая модель не скатится в три оттенка одного.
3. **План каждого направления до кода** (как во frontend-design): токены, роли шрифтов, ASCII-каркас экранов, принципы; самопроверка «что тут дефолтное» и правка.
4. **Мокапы**: статичный HTML тех же ключевых экранов для каждого направления, токены в `tokens.css`, реалистичный текст (без выдуманных отзывов и цифр), заглушки изображений.
5. **Проверка скриптом** (`lint.mjs`, в браузере, тем же извлечением, что wd-scan): пол качества (контраст, фокус, цели, reduced-motion, нет горизонтального скролла на 390/768/1440),
   детектор «тел» ИИ-дизайна, **мера различия** направлений (палитры, шрифты, радиусы, раскладка); до 3 кругов исправлений.
6. **Страница сравнения** `index.html`: три направления рядом — скриншоты, токены, плюсы и минусы, итог проверки → пользователь утверждает одно (или просит смешать).
7. **Выход**: утверждённое направление снимается wd-scan (режим `serve`) → `design-context/`, где всё — канон. Дальше страницы и фичи делает wd-fit.

Доработка (2026-11-18), после оценки «скилл тонкий»:
- **UI-кит** `kit.html` — третий обязательный экран: все детали и состояния с `data-part`; после утверждения — канон с именами.
  Без него контекст из двух экранов был бедным (нет полей, ошибок, таблиц), и wd-fit было не из чего собирать.
- **Две темы**: у operate/read по умолчанию, вторая выводится из палитры с проверкой контраста; lint и approve их учитывают.
- **Кириллица**: из 16 шрифтовых пар только 5 её поддерживали — русские заголовки падали в Georgia. Флаг `cyr` проверяется
  по Google Fonts (`deal.mjs --validate --fonts`), для русского брифа берутся только такие пары; пар теперь 31 (20 с кириллицей).
- **Каталоги шире**: архетипов 17 → 33 (минимум 7 на режим), палитр 16 → 28, статусные цвета и цвет ссылки в токенах.
- **Отрасли** (13): автоопределение по брифу, правила в PLAN.md, ограничения палитры и шрифтов.
- Ещё не сделано: сайты-ориентиры («как у Stripe, но теплее») и проверка вкуса по скриншотам для моделей со зрением.

Решено: каталоги — свои компактные (идеи пересказаны, данные не копировались — references/sources.md); 2 экрана на направление по умолчанию.
