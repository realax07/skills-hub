# Пример 1: повторяющийся процесс → скилл со скриптом и шаблоном

## Запрос

> каждую пятницу прошу тебя собрать changelog из git log, у нас conventional commits. надоело объяснять одно и то же — сделай из этого скилл, чтобы и в codex работал

## Ход работы

1. **Понять.** В диалоге выше пользователь уже дважды поправлял результат: «не пиши хэши», «breaking changes — отдельным разделом сверху»,
   «chore и ci не нужны». Это правила скилла. Уточнить одним вопросом: «Формат — Keep a Changelog, диапазон — от последнего тега до HEAD?» → «да».
2. **Место.** Не хаб; нужен и Claude, и Codex → глобально в `~/.agents/skills/` (читают оба) — пользователь подтвердил.
3. **Каркас.** `python3 scripts/init_skill.py changelog-writer --dest ~/.agents/skills --script collect_commits`
4. **Детерминированное — в скрипт.** Разбор `git log` по типам, scope, `!`/`BREAKING CHANGE` агент каждый раз писал бы заново,
   и в регулярке легко ошибиться → `scripts/collect_commits.py <репо> [--since <тег>] --json`.
   Писать текст для людей — суждение → остаётся инструкцией.
5. **Шаблон** разделов — `assets/changelog.md`. Правила пользователя — в `references/rules.md` с причинами.
6. **Примеры**: `examples/01-release.md` (полный результат), `examples/02-noisy-history.md` (плохо: пересказ коммитов / хорошо: для пользователя).
7. **Тесты**: `new_eval.py` ×2 — обычный репо с тегом; репо без тегов и с коммитами без типа (`--files` с bundle-репо).
8. **Проверка**: `validate_skill.py ~/.agents/skills/changelog-writer --strict --run-scripts` → 0 ошибок; чек-лист.

```markdown
name: changelog-writer
description: Собирает changelog и release notes из истории git с conventional commits — группирует изменения по типам, выносит breaking changes наверх, пишет понятный пользователю текст в формате Keep a Changelog. Используй, когда пользователь просит changelog, заметки к релизу, «что изменилось с прошлой версии», подготовить релиз или описание версии — даже если он просто называет тег, ветку или диапазон коммитов.

# Changelog Writer

Превращает историю git в changelog для людей: что появилось, что исправлено, что сломается при обновлении.

## Процесс

1. **Диапазон.** По умолчанию — от последнего тега до HEAD. Если тегов нет — спроси, с какого коммита или даты.
2. **Сбор.** `python3 scripts/collect_commits.py <репо> --since <тег> --json` → коммиты по типам
   (`feat`, `fix`, `perf`, `breaking`, `other`). Код 1 — не git-репо или нет такого тега: скажи пользователю.
3. **Текст.** Заполни [assets/changelog.md](assets/changelog.md). Пиши, что изменилось для пользователя, а не что сделал разработчик;
   похожие коммиты объединяй. Правила — [references/rules.md](references/rules.md).
4. **Проверка.** Каждый `breaking` попал в раздел «Breaking changes»; нет хэшей, `chore`, `ci`, мерджей.
5. **Отчёт.** Покажи changelog и спроси, дописать ли в CHANGELOG.md.

## Ключевые правила

- Breaking changes — отдельным разделом первым: это то, что читатель обязан увидеть до обновления.
- Без хэшей и имён авторов — changelog читают пользователи, им это шум.
- `chore`, `ci`, `test`, `build` не включай: они не меняют поведение продукта.
- Коммиты без типа — в `other`; посмотри diff и отнеси к разделу, если смысл ясен.

## Ресурсы

| Путь | Что там | Когда открывать |
|---|---|---|
| `scripts/collect_commits.py` | git log → JSON по типам | шаг 2, не читать целиком |
| `assets/changelog.md` | шаблон разделов | шаг 3 |
| `references/rules.md` | группировка, крайние случаи (revert, squash, monorepo) | шаг 3, сомнения |
| `examples/` | полный релиз; шумная история плохо/хорошо | перед первым запуском |
```

## Почему так

- Исправления пользователя из диалога стали правилами **с причинами** — так агент обработает и `docs:`, о котором пользователь не говорил.
- Разбор коммитов — скрипт: детерминирован и легко ошибиться. Текст — инструкция: нужно суждение.
- `~/.agents/skills` выбран, потому что пользователь упомянул Codex ([references/agents.md](../references/agents.md)).
- Второй тест-кейс — на крайний случай (нет тегов, мусорные коммиты), где без скилла агент чаще всего ошибается.
