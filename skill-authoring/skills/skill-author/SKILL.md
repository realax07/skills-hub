# Skill Author

Делает из задачи пользователя готовый к установке скилл со всей структурой и проверяет его,
а не просто пишет один SKILL.md. Хороший скилл — это три уровня загрузки (description → тело → ресурсы),
код для того, что не стоит каждый раз писать заново, и тесты, по которым видно, что он работает.

Пути к скриптам — относительно папки этого скилла. Скрипты — Python 3.9+ без зависимостей.

## Процесс

1. **Понять, что даёт скилл.** Выясни (из диалога, файлов, вопросов): какую задачу решает, на каких запросах
   должен срабатывать, какой результат, какие шаги детерминированы, нужны ли внешние пакеты.
   Если в разговоре уже есть рабочий процесс — извлеки шаги, исправления пользователя и форматы оттуда,
   а не придумывай заново. Спроси только то, что нельзя вывести. Почему: скилл, собранный по догадкам, срабатывает не там и учит не тому.
2. **Выбрать место.** Если работаешь внутри репо-хаба скиллов (есть `agents.conf` и папки `<тема>/skills/`) — следуй его AGENTS.md
   и создавай в теме. Иначе — папка скиллов агента или проекта (таблица — [references/agents.md](references/agents.md))
   или та, что назвал пользователь. Имя — kebab-case, уникальное: агенты кладут скиллы в одну плоскую папку.
3. **Каркас.** `python3 scripts/init_skill.py <имя> --dest <папка>` (в хабе: `--topic <тема>` вместо `--dest`).
   Флаги: `--lang py|node|none` — стартовый скрипт, `--setup py|node` — установщик зависимостей,
   `--evals-files` — тест-кейс с входными файлами. Получишь всю структуру с заглушками.
4. **Метаданные (frontmatter).** Пиши первыми: до срабатывания агент видит только `name` и `description`.
   Поэтому всё, что решает «брать или нет», — только здесь: что делает, когда применять (формулировками пользователя,
   с синонимами и косвенными запросами), чуть настойчивое «даже если…» и границы «не применяй для…».
   Плюс `compatibility`, если есть зависимости. Правила и разборы — [references/description.md](references/description.md).
5. **Тело SKILL.md** — только про выполнение задачи: входные данные, процесс шагами, ключевые правила с причинами,
   формат результата, короткий пример, таблица ресурсов «путь — что там — когда открывать».
   Раздела «когда применять» в теле нет: тело грузится уже после решения, условия там не работают и только тратят контекст.
   До ~500 строк; всё подробное — в ресурсы.
   Полный свод — [references/rules.md](references/rules.md).
6. **Ресурсы.** `references/rules.md` — правила, крайние случаи, типичные ошибки. `examples/` — один файл на разбор,
   хотя бы один «плохо / хорошо». `scripts/` — детерминированные и повторяющиеся шаги
   ([references/scripts.md](references/scripts.md)). `assets/` — шаблоны результата. Удали пустые папки и
   шаблонные файлы, которые не пригодились, — кроме `evals/`.
7. **Тесты.** 2–3 реалистичных запроса: типичный и крайний. `python3 scripts/new_eval.py <скилл> <кейс> --prompt … --expect … --grader … [--files <папка>]`.
   Формат и как писать грейдеры — [references/evals.md](references/evals.md).
8. **Проверка.** `python3 scripts/validate_skill.py <скилл> --strict --run-scripts` — без ошибок и заглушек.
   Затем пройди [assets/review-checklist.md](assets/review-checklist.md). Если можно — прогони пару тестовых запросов
   со скиллом и без и сравни: так видно, что скилл реально что-то меняет.
9. **Отчёт.** Где лежит скилл, дерево файлов, что делает каждый скрипт, как установить и проверить,
   что осталось на пользователе (например, вписать реальные пакеты в setup).

Улучшение существующего скилла — те же шаги 4–8 над ним, без `init_skill.py`; сначала
`validate_skill.py` для списка проблем. Разбор — [examples/03-improve-bloated-skill.md](examples/03-improve-bloated-skill.md).

## Ключевые правила

- **Прогрессивная загрузка.** description всегда в контексте, тело — при срабатывании, ресурсы — по ссылке.
  Поэтому в теле — процесс и главное, а у каждого ресурса — явное «когда открывать»: файл, о котором SKILL.md молчит, агент не откроет.
- **Условия срабатывания — в метаданных, выполнение — в теле.** Триггеры, синонимы и границы живут только в description:
  тело грузится уже после решения. Тело отвечает на вопрос «как сделать», а не «когда браться».
- **Объясняй почему, а не кричи.** «Делай X, потому что Y» вместо «ВСЕГДА X»: модель, понимающая цель, сама справится с крайними случаями.
- **Общие принципы, не подгонка.** Скилл вызовут на тысячах разных запросов; правило, написанное под один пример, сломает остальные.
- **Код — для повторяющегося.** Если агент на каждом запуске писал бы одинаковый парсер или проверку — это скрипт
  с `--help`, `--json` и ненулевым кодом при ошибке. Суждение и вкус в скрипт не выносятся.
- **Агент-нейтрально.** Без инструментов и путей одного агента, пути — относительно папки скилла. Скилл ставят в разные агенты.
- **Под самую слабую модель.** Скилл запускают и быстрые модели без зрения (DeepSeek, GLM Flash, Kimi): точные команды,
  шаги с явными развилками и поведением «спросить некого», механика — в скриптах, текстовая альтернатива картинкам,
  таблица «симптом → что делать». Подробно — [references/rules.md](references/rules.md#под-любые-модели).
- **Зависимости явно.** Всё вне стандартной библиотеки — в `compatibility` и в установщик setup (`--check`), ставится вне папки скилла.
- **Без сюрпризов.** Содержимое соответствует описанию: никакой скрытой отправки данных и обхода защит.

## Формат результата

```
<имя>/
├── SKILL.md          frontmatter: name (= папка), description (что + когда + границы); опц. compatibility, license, metadata
│                     тело: входные данные, процесс, правила, формат результата, пример, ресурсы
├── references/       rules.md + по файлу на тему/вариант (с оглавлением, если > 300 строк)
├── examples/         01-типичный.md, 02-крайний-плохо-хорошо.md
├── scripts/          CLI-скрипты; setup.py или setup.mjs, если есть зависимости
├── assets/           шаблоны результата, конфиги, иконки
└── evals/<кейс>/     prompt.md, case.yaml, graders/NN-*.md, [files/, place-files.sh]
```

## Пример

**Запрос:** «каждую пятницу прошу тебя собрать changelog из git log по conventional commits — сделай из этого скилл»
**Результат:** `changelog-writer/` — description со словами «changelog, release notes, что изменилось, заметки к релизу»;
процесс «диапазон → сбор → группировка → текст»; collect_commits.py в scripts/ (git log → JSON по типам, детерминированно);
шаблон разделов changelog.md в assets/; references/rules.md (breaking changes, коммиты без типа, мерджи);
пример «плохо: пересказ каждого коммита / хорошо: сгруппировано для пользователя»; 2 тест-кейса; валидатор зелёный.
Полный разбор — [examples/01-workflow-to-skill.md](examples/01-workflow-to-skill.md).

- [examples/01-workflow-to-skill.md](examples/01-workflow-to-skill.md) — из повторяющегося процесса в скилл со скриптом и шаблоном
- [examples/02-description-bad-good.md](examples/02-description-bad-good.md) — description, который не срабатывает, и как его исправить
- [examples/03-improve-bloated-skill.md](examples/03-improve-bloated-skill.md) — раздутый SKILL.md с кодом внутри → полная структура

## Ресурсы

| Путь | Что там | Когда открывать |
|---|---|---|
| `references/rules.md` | полный свод правил: анатомия, стиль, крайние случаи, ошибки | перед шагом 5, при любых сомнениях |
| `references/description.md` | как писать description, формулы, плохо/хорошо | шаг 4, скилл плохо срабатывает |
| `references/scripts.md` | когда нужен скрипт, конвенции CLI, зависимости и setup | шаг 6, если в скилле есть код |
| `references/evals.md` | формат evals, грейдеры, входные файлы | шаг 7 |
| `references/agents.md` | куда агенты кладут скиллы, переносимость | шаг 2, отчёт об установке |
| `examples/` | три разбора: процесс → скилл, description, рефакторинг | перед первым скиллом, для калибровки |
| `scripts/init_skill.py` | каркас скилла из шаблонов (`--help`) | шаг 3 |
| `scripts/new_eval.py` | новый тест-кейс в evals/ (`--help`) | шаг 7 |
| `scripts/validate_skill.py` | проверка скилла, `--json` для разбора | шаг 8 и после каждой правки |
| `assets/skeleton/` | шаблоны файлов скилла (их копирует init_skill.py) | менять, только если меняешь сам каркас |
| `assets/extras/` | шаблоны Node-скрипта, установщиков, place-files.sh | вручную, если флаги init_skill.py не подошли |
| `assets/review-checklist.md` | чек-лист перед сдачей | шаг 8 |
