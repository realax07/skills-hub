# Правила: Skill Author

Полный свод правил создания скилла. SKILL.md держит только главное и ссылается сюда.
Основа — спецификация Agent Skills (agentskills.io) и гайд skill-creator от Anthropic, в агент-нейтральном виде.

## Анатомия

| Путь | Обязателен | Что там |
|---|---|---|
| `SKILL.md` | да | frontmatter + инструкции. Один на скилл — вложенные SKILL.md агенты примут за отдельные скиллы |
| `references/` | почти всегда | правила, справка, варианты под фреймворки/платформы |
| `examples/` | почти всегда | разобранные примеры вход → ход работы → результат |
| `scripts/` | если есть детерминированные шаги | исполняемый код |
| `assets/` | если результат строится по шаблону | шаблоны, конфиги, иконки, шрифты — то, что копируют в результат |
| `evals/` | да | тест-кейсы; инсталляторы агентам их обычно не ставят |

Пустые папки и неиспользованные шаблонные файлы удаляй: они обещают агенту содержимое, которого нет. `evals/` оставляй всегда.

## Прогрессивная загрузка

1. **name + description** — всегда в контексте всех скиллов, ~100 слов. По ним агент решает, брать ли скилл.
2. **Тело SKILL.md** — грузится при срабатывании. До ~500 строк, иначе вытесняет рабочий контекст.
3. **Ресурсы** — открываются по ссылке из тела. Объём не ограничен; скрипты можно запускать, не читая.

Следствия:
- У каждого ресурса в теле — «когда открывать». Ссылка без условия либо игнорируется, либо читается всегда (и тратит контекст).
- Справочник > 300 строк — с оглавлением: агент читает его кусками и должен найти нужный раздел.
- Варианты (React / Vue, AWS / GCP) — по файлу на вариант, и в теле правило выбора. Тогда грузится только нужный.

## Frontmatter

| Ключ | Правило |
|---|---|
| `name` | kebab-case, до 64 символов, совпадает с именем папки, уникален среди скиллов агента |
| `description` | одна строка, до 1024 символов, без угловых скобок. **Все условия срабатывания**: что делает, когда применять, косвенные формулировки, границы «не применяй для…» ([description.md](description.md)) |
| `compatibility` | до 500 символов: рантайм, пакеты, браузеры, объём, куда ставится. Только если есть внешние зависимости |
| `license`, `metadata`, `allowed-tools` | по необходимости. Другие ключи часть агентов отвергает |

Многострочный description через `|` или `>` разбирается не всеми агентами — пиши одной строкой.

**Метаданные решают «брать или нет», тело — «как сделать».** До срабатывания агент видит только `name` и `description`
всех установленных скиллов; тело грузится уже после решения. Поэтому триггеры, синонимы, примеры запросов и границы
со соседними скиллами живут только в description, а в теле раздела «когда применять» нет — там он не влияет на выбор
и только занимает контекст. Если условий много и в 1024 символа они не влезают — сократи формулировки и оставь самые частые,
но не переноси остаток в тело.

Пример полного frontmatter:

```yaml
---
name: pdf-extract
description: Извлекает из PDF текст, таблицы и картинки в JSON, Markdown и CSV, распознаёт сканы через OCR. Используй, когда пользователь даёт PDF (счёт, договор, отчёт, выписку) и просит достать текст, таблицу, цифры или картинки, перевести PDF в Excel или Markdown — даже если просто пишет «что в этом файле». Не применяй для создания и редактирования PDF — для этого нужен другой инструмент.
compatibility: Python 3.9+. pypdf и pdfplumber ставит scripts/setup.py (≈20 МБ, в ~/.cache/agent-skills/pdf-extract).
license: MIT
metadata:
  version: "1.2"
---
```

## Тело SKILL.md

Порядок, который хорошо работает:

Тело — только про выполнение задачи. Раздела «когда применять» нет (см. [Frontmatter](#frontmatter)).

1. Заголовок и 1–3 предложения: какую задачу решает и какой результат. Если подход неочевиден — одно предложение «почему так».
2. **Входные данные** (если есть) — что нужно от пользователя и что делать, если этого нет.
3. **Процесс** — нумерованные шаги. В каждом — что сделать, какой скрипт вызвать и что он вернёт, когда открыть какой ресурс.
   Последние шаги — проверка результата и отчёт пользователю.
4. **Ключевые правила** — 5–10 пунктов с причинами.
5. **Формат результата** — точный шаблон, если формат строгий (или ссылка на `assets/`).
6. **Пример** — короткий, плюс ссылки на полные разборы.
7. **Ресурсы** — таблица «путь — что там — когда открывать».

Пути — относительно папки скилла (`scripts/x.py`, а не абсолютные и не `~/.claude/skills/...`): скилл ставят в разные места.

## references/

- `rules.md` — обязательные правила с причинами, рекомендации, таблица крайних случаев, типичные ошибки.
- Отдельный файл на большую подтему (формат плана, работа с API, варианты платформ). Один уровень вложенности: ссылки из SKILL.md, а не цепочки ссылок между справочниками.
- Пиши для агента, который уже в задаче: конкретные значения, команды, таблицы решений. Не пересказывай тело.

## examples/

- Один файл — один пример. Структура: запрос (как его реально напишет человек) → ход работы → результат целиком → почему так (какие правила сработали).
- Обязательно хотя бы один «плохо / хорошо» на крайний случай: контраст калибрует качество лучше, чем описание.
- Примеры разнообразные: если все три про одно и то же, агент переобучится на частный случай.
- Результат в примере — настоящий, а не «...здесь будет текст». Агент копирует уровень детализации.

## scripts/ и assets/

- Скрипт — когда шаг детерминирован или агент иначе каждый раз пишет одинаковый код. Подробно — [scripts.md](scripts.md).
- `assets/` — то, что попадает в результат (шаблоны, конфиги, стили). Агент копирует или заполняет их, а не читает как инструкции.
  Поэтому в шаблонах — плейсхолдеры и минимум пояснений; инструкции к шаблону — в SKILL.md.

## Стиль инструкций

- Повелительное наклонение: «Проверь», «Сгенерируй», «Спроси».
- Причина рядом с правилом. «Не используй хэш-классы в селекторах — они меняются при каждой сборке» сильнее, чем «НИКОГДА не используй хэш-классы».
- Капс, «ОБЯЗАТЕЛЬНО», «КРИТИЧНО» — признак, что причина не объяснена. Модель и так старается следовать инструкциям; перекрик делает её негибкой.
- Без агент-специфики: не «вызови инструмент Read», а «прочитай файл»; не «используй TodoWrite», а «составь план».
- Язык — язык пользователя/хаба. Имена файлов, ключи, команды — латиницей.
- Пиши про общий случай. Если правило появилось из-за одного теста — переформулируй его как принцип.

## Под любые модели

Скилл, установленный в хаб, запускают разные модели — в том числе быстрые, дешёвые и без зрения.
Сильная модель достроит неявное, слабая — нет: придумает флаг, решит за пользователя, обойдёт ошибку вручную.
Пиши под самую слабую:

- **Точные команды.** Полная команда с плейсхолдерами (`node <skill>/scripts/x.mjs <out> --json`), а не «запусти скрипт разведки».
  Слабая модель не достроит недостающий флаг, а придумает свой.
- **Шаги по порядку, развилки явно.** Нумерованный процесс; у каждого решения — условие и вариант по умолчанию
  («нет X — делай Y»). Чего нельзя решать за пользователя — так и написано, с поведением «спросить некого»
  (автономный прогон): что оставить незаданным и что написать в отчёте.
- **Детерминированное — в скрипты.** Всё, где можно ошибиться руками (правка JSON, подсчёты, разбор вывода), —
  CLI с проверкой аргументов и понятной ошибкой. Суждение оставь модели, механику — коду.
- **Без обязательного зрения.** Если шаг опирается на картинки или скриншоты — дай текстовую альтернативу
  (список со значениями, `--json`): часть моделей изображений не видит.
- **Таблица «Если что-то не так».** Симптом → что делать. Иначе слабая модель обходит ошибку вручную и портит результат.
- **Проверка результата шагом процесса.** Команда проверки и критерий «готово» — чтобы модель не объявляла успех на глаз.

Проверка: прочитай SKILL.md так, будто ты не знаешь предметной области и не видишь картинок, — на каком шаге пришлось бы угадывать?
Если тесты можно прогнать на слабой модели — прогони: её ошибки и есть список неявных мест.

## Крайние случаи

| Ситуация | Что делать | Почему |
|---|---|---|
| В процессе есть вопрос пользователю, а скилл могут запустить автономно | Опиши поведение «спросить некого»: что оставить незаданным, что вписать в отчёт; решения владельца не принимать молча | Иначе модель угадает и сделает необратимое (создаст файл, выберет политику) |
| Шаг опирается на картинки или скриншоты | Текстовая альтернатива: список значений, `--json` | Не все модели видят изображения |
| Пользователь описал задачу в одну строку | Выясни триггеры, результат и шаги вопросами (2–4 вопроса), остальное выведи сам | Без этого description и процесс будут угаданы |
| Процесс уже есть в текущем диалоге | Извлеки шаги, исправления и форматы из диалога, подтверди у пользователя | Пользователь уже показал, как правильно |
| Скилл с таким именем уже есть | Улучшай существующий или выбери другое имя; не перезаписывай | Чужой скилл можно сломать; init_skill.py откажется сам |
| Задача субъективная (стиль, дизайн, тон) | Грейдеры — на проверяемые признаки (структура, наличие разделов), вкус — на ревью глазами | Формальная проверка вкуса даёт ложную уверенность |
| Нужна библиотека не из stdlib | `compatibility` + установщик setup с `--check`, пиннованные версии, установка вне папки скилла | Скилл бывает симлинком в git или read-only копией |
| Нужен системный пакет / sudo | Проверь и скажи пользователю, что поставить; сам не ставь | Установка системного ПО — решение пользователя |
| Скилл под несколько фреймворков | Общий процесс в SKILL.md + `references/<вариант>.md` и правило выбора | Грузится только нужный вариант |
| Скилл почти целиком — один скрипт | Всё равно SKILL.md с процессом, входами, интерпретацией результата и ошибками | Агенту нужно знать, когда и как вызвать и что делать при сбое |
| Нужен доступ к секретам/аккаунтам | Скилл просит у пользователя токен/сессию, не хранит их в файлах скилла | Скиллы копируют и публикуют |
| Работа внутри репо-хаба скиллов | Следуй его AGENTS.md: тема, README темы, валидатор хаба | У хаба свои соглашения и инсталлятор |

## Типичные ошибки

- **description только «что», без «когда»** → добавь фразы и контексты срабатывания, косвенные формулировки.
- **Раздел «когда применять» в теле** → перенеси всё в description (триггеры, синонимы, границы) и удали раздел: тело грузится уже после решения.
- **Границы с соседними скиллами в теле («не применяй для…»)** → тоже в description: иначе соседние скиллы конкурируют за запрос.
- **Всё в одном SKILL.md на 900 строк** → процесс в теле, правила — в `references/rules.md`, разборы — в `examples/`, код — в `scripts/`.
- **Код в теле SKILL.md, который агент перепечатывает каждый раз** → вынеси в `scripts/` с CLI.
- **Ресурсы есть, но SKILL.md о них молчит** → строка в таблице ресурсов с «когда открывать».
- **Пример-заглушка «...»** → полный результат, иначе агент не поймёт уровень детализации.
- **Тест-кейсы вида «используй скилл X для задачи Y»** → запрос так, как его напишет человек, без имени скилла.
- **Пути под одного агента** (`~/.claude/...`, имена инструментов) → относительно папки скилла и нейтральные глаголы.
- **Зависимости ставятся в папку скилла** → в `~/.cache/agent-skills/<скилл>/` (Windows: `%LOCALAPPDATA%\agent-skills\<скилл>\`).
- **«Запусти скрипт разведки» без команды** → полная команда с плейсхолдерами: слабая модель не угадает флаги.
- **«Отредактируй JSON вот так»** как обязательный шаг → CLI, который правит и проверяет сам.
- **Шаг «посмотри вырезки и реши»** без текстовой альтернативы → модели без зрения его не пройдут.
- **Сдача без проверки** → `validate_skill.py --strict --run-scripts` и чек-лист.
