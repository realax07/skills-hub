# Анализ влияния: отмена оплаченного заказа до отправки с возвратом денег

Корень репозитория: `.../scratchpad/big/eShop`. Все пути ниже относительно него. Источник: только код, тесты, проекты, конфиги.

## 1. Затронутое поведение

Меняется:
- Отмена запрещена для `Paid` и `Shipped`: `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:142-153` (`SetCancelledStatus` бросает `OrderingDomainException` при `Paid`/`Shipped`, `Order.cs:144-148`, текст — `Order.cs:180-183`). Доработка должна разрешить `Paid` (и оставить запрет для `Shipped`, а также для уже `Cancelled`).
- Отмена оплаченного заказа сегодня не возвращает деньги: возврата нет нигде (в `src/PaymentProcessor/` только обработчик `OrderStatusChangedToStockConfirmedIntegrationEvent` и публикация успеха/ошибки оплаты: `PaymentProcessor/IntegrationEvents/EventHandling/OrderStatusChangedToStockConfirmedIntegrationEventHandler.cs:9-33`). Поиск по `refund`/`возврат` в `src/` и `tests/` ничего не даёт.
- Отмена не возвращает товар на склад: склад списывается только на `Paid` (`Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToPaidIntegrationEventHandler.cs:13-18`), на `Cancelled` Catalog не подписан (подписки: `Catalog.API/Extensions/Extensions.cs:31-33`, только `AwaitingValidation` и `Paid`). Для отмены до оплаты это корректно (склад ещё не списан), для отмены после оплаты — нужен возврат остатка.
- Единая команда `CancelOrderCommand(int OrderNumber)` (`Ordering.API/Application/Commands/CancelOrderCommand.cs:3`) используется двумя разными сценариями: клиентская отмена (`OrdersApi.cs:11,22-49`) и автоотмена при ошибке оплаты (`Ordering.API/Application/IntegrationEvents/EventHandling/OrderPaymentFailedIntegrationEventHandler.cs:12,21`). Если расширить `SetCancelledStatus`, автоотмена по `OrderPaymentFailed` не должна запускать возврат (деньги не списаны). Нужно различать причину/источник.
- Отмена по нехватке склада (`SetCancelledStatusWhenStockIsRejected`, `Order.cs:155-168`) меняет статус на `Cancelled` без доменного события, поэтому интеграционного события `OrderStatusChangedToCancelled` не будет (WebApp не получит уведомление) — существующий пробел, остаётся как есть.

Сохраняется и на это опирается изменение:
- Конечный автомат статусов: `Submitted(1) -> AwaitingValidation(2) -> StockConfirmed(3) -> Paid(4) -> Shipped(5)`, `Cancelled(6)`: `Ordering.Domain/AggregatesModel/OrderAggregate/OrderStatus.cs:6-14`. Переходы вперёд — с проверкой «из какого статуса» и тихим игнором неподходящего (`Order.cs:99-128`), отгрузка — только из `Paid` (`Order.cs:130-140`).
- Идемпотентность по заголовку `x-requestid` (`OrdersApi.cs:23,27-30,32`, `Ordering.API/Application/Commands/IdentifiedCommandHandler.cs:41-48`; повторный запрос возвращает `true`: `CancelOrderCommandHandler.cs:44-47`).
- Каждый переход статуса порождает доменное событие -> обработчик кладёт интеграционное событие в outbox внутри транзакции -> публикация после коммита (`Order.cs:103,112,123,139,152`; `Ordering.API/Application/DomainEventHandlers/*`; `Ordering.API/Application/Behaviors/TransactionBehavior.cs:34-52`).
- «Grace period»: заказ в `Submitted` ждёт 1 минуту (`OrderProcessor/appsettings.json:14-17`), потом `OrderProcessor` публикует `GracePeriodConfirmed` -> `AwaitingValidation` (`OrderProcessor/Services/GracePeriodOrdersRepository.cs:24-28`, `GracePeriodManagerService.cs:50-60`, `Ordering.API/Application/IntegrationEvents/EventHandling/GracePeriodConfirmedIntegrationEventHandler.cs:19,28`, `SetAwaitingValidationOrderStatusCommandHandler.cs:27`). Текущая отмена (клиент мобильный) возможна только в этом окне: кнопка видна только при `Submitted` (`ClientApp/ViewModels/OrderDetailViewModel.cs:38`, `ClientApp/Views/OrderDetailView.xaml:76`).
- Сумма заказа считается как `Σ Units*UnitPrice` без учёта `Discount`: `Order.cs:185`, `Ordering.API/Application/Queries/OrderQueries.cs:26,46`. Сумма возврата должна согласоваться с этим же правилом (или с тем, что реально «списал» процессор — но процессор суммы не получает, см. разд. 3).
- Оплата в проекте имитируется конфигом: `PaymentOptions:PaymentSucceeded=true` (`PaymentProcessor/appsettings.json:14-16`, `PaymentProcessor/PaymentOptions.cs:5`, `PaymentProcessor/Program.cs:8-9`). Реального «платёжного процессора» (транзакций, id платежа, суммы, API) в коде нет — его придётся вводить как модель (или как симулятор возврата).

(б) Ответ при отмене оплаченного заказа: либо `200` + «возврат инициирован», либо `202 Accepted` (возврат асинхронный через шину) — клиенты, которые ждут `200`, должны принять оба. (в) Тела ответа нет — если нужно вернуть статус возврата/сумму, это новое поле ответа (сейчас `Results<Ok, ...>` без тела, `OrdersApi.cs:22`).

То же отсутствует у `GET /api/orders/{orderId}` (`OrdersApi.cs:80-91`, `OrderQueries.cs:6-35`) и у `PUT /api/orders/ship` (`OrdersApi.cs:12,51-78`, роли нет).

Если вводится новый статус (`Refunding`/`Refunded`/`RefundFailed`), то все клиенты увидят новую строку (разд. 4); ничего не ломается на уровне схемы, но UI-логика, завязанная на значения, нуждается в правке. Возможное новое поле в `Order`/`OrderSummary` (например `refundStatus`, `refundedAmount`) — добавление, обратно совместимо (`OrderViewModel.cs:11-32`).

- gRPC: Basket-gRPC к отмене не относится (в `src/Basket.API` нет обработки отмены); `.proto`-файлы в заказах отсутствуют. Не затрагивается.

## 3. События

Шина: RabbitMQ, direct-обменник `eshop_event_bus`, routing key = короткое имя класса события (`EventBusRabbitMQ/RabbitMQEventBus.cs:20,33,97-102`); потребитель находит тип по имени в `EventBusSubscriptionInfo` (`RabbitMQEventBus.cs:192-196`, `EventBus/Extensions/EventBusBuilderExtensions.cs:27-36`). Следствия: (1) каждый сервис держит собственную копию класса события, совпадать должны имя и имена полей; (2) исключение в обработчике логируется и сообщение всё равно подтверждается (нет повторов и DLX): `RabbitMQEventBus.cs:170-180`; (3) `mandatory: true` (`RabbitMQEventBus.cs:100`) — публикация события, на которое никто не подписан/нет привязанной очереди, не маршрутизируется. Событие должно иметь суффикс `IntegrationEvent`, иначе outbox его не найдёт (`IntegrationEventLogEF/Services/IntegrationEventLogService.cs:15,28`).

## 4. Потребители и сервисы

Придётся менять:
- **Ordering.API** — основной: домен (`Order.cs`), команды, доменные/интеграционные обработчики, новые подписки (разд. 6).
- **Ordering.Domain / Ordering.Infrastructure** — поля заказа для платежа/возврата, статусы, миграция (разд. 5).
- **PaymentProcessor** — единственный «платёжный процессор»: сейчас только имитация оплаты; нужен обработчик возврата (имитация или реальный вызов), конфиг исхода возврата по аналогии `PaymentOptions` (`PaymentProcessor/PaymentOptions.cs:5`, `appsettings.json:14-16`). Сервис не имеет БД/состояния (`PaymentProcessor/Program.cs`), хранить связку «платёж ↔ заказ» негде; для идемпотентности возврата нужно решение (хранить в Ordering и передавать ключ).
- **Catalog.API** — вернуть остатки при отмене оплаченного заказа (`Catalog.API/Extensions/Extensions.cs:31-33`, `Model/CatalogItem.cs:47-66`).
- **Webhooks.API** и **WebhookClient** — по решению: новый тип вебхука (`Webhooks.API/Model/WebhookType.cs:3-8`, `WebhookClient/Services/WebhookType.cs:3-8`; хранится как `int`: `Webhooks.API/Migrations/20230925222606_Initial.cs:21` — миграция не нужна). - **WebApp (витрина)**: есть уведомление об изменении статуса (`WebApp/Extensions/Extensions.cs:45-50`, `OrderStatusNotificationService.cs:27-35`, `Components/Pages/User/OrdersRefreshOnStatusChange.razor:23-34`), но нет кнопки отмены и вызова API: `WebApp/Services/OrderingService.cs:7-18` имеет только `GetOrders` и `CreateOrder`; `Orders.razor:38-56` показывает только номер, дату, сумму, статус. ## 8. Риски

Транзакции и outbox:
- Событие в outbox пишется внутри транзакции команды, публикуется после коммита: `TransactionBehavior.cs:34-52`, `OrderingIntegrationEventService.cs:13-41`. Но при сбое публикации событие помечается `PublishedFailed` (`OrderingIntegrationEventService.cs:27-32`, `IntegrationEventLogService.cs:56-59`) и больше не повторяется нигде в коде (повторной отправки нет). Для «запроса возврата» это означает: заказ отменён, а возврат не запущен — деньги зависнут. Нужен механизм повторной отправки/сверки (например, фоновая задача по `PublishedFailed` или по заказам в состоянии «ожидает возврата»).
- Доменные события обрабатываются до `SaveChanges` в той же транзакции (`OrderingContext.cs:47-62`); внутри обработчиков вызывается `AddAndSaveEventAsync` со своим `SaveChangesAsync` (`IntegrationEventLogService.cs:34-44`).
- `IdentifiedCommandHandler` пишет `ClientRequest` и затем глотает исключение внутреннего обработчика (`IdentifiedCommandHandler.cs:48,99-102`); внешняя транзакция при этом коммитится. Итог: неудачная отмена (например, запрет перехода) «сжигает» `x-requestid`, а повтор с тем же ключом вернёт `200` как «дубликат» (`CancelOrderCommandHandler.cs:44-47`), хотя заказ не отменён. Для денежной операции такое поведение недопустимо — нужно либо откат записи запроса при ошибке, либо не отвечать `true` на дубликат неуспешной команды.
- `PublishEventsThroughEventBusAsync` вызывается после коммита и внутри `ExecutionStrategy` (`TransactionBehavior.cs:32-53`): при повторе стратегии (retry Npgsql) возможен повтор публикации -> дубль `OrderRefundRequested`. Возврат на стороне процессора должен быть идемпотентным по `OrderId`.
- Шина: ошибка обработчика не повторяется и не уходит в DLX (`RabbitMQEventBus.cs:170-180`). Если обработчик результата возврата в Ordering упадёт, заказ останется «возврат в процессе» навсегда. Нужны сверка по таймауту и логирование.
- `mandatory: true` (`RabbitMQEventBus.cs:100`): событие, на которое нет привязанной очереди (сервис ещё не стартовал/не подписался), не будет доставлено. Привязка очередей происходит при старте потребителя (`RabbitMQEventBus.cs:258,281`). Порядок выкладки: сначала подписчики (PaymentProcessor, Catalog), потом публикующий Ordering.

Гонки и порядок событий:
- Отмена vs отгрузка: у `Order` нет токена конкурентности (поиск `RowVersion|Concurrency|xmin` в Infrastructure/Domain — пусто), `ReadCommitted` (`OrderingContext.cs:68`). Две параллельные команды (`cancel` и `ship`) обе читают `Paid` и обе пишут: последняя побеждает без ошибки -> заказ `Shipped`, но возврат инициирован (или `Cancelled`, но событие `Shipped` ушло и вебхук `OrderShipped` отправлен). Нужен `rowversion`/`xmin` или условное обновление `WHERE "OrderStatus"='Paid'`. `ShipOrder` и сейчас доступен без ролевой проверки (`OrdersApi.cs:12,51-78`).
- Отмена vs подтверждение оплаты (самое тонкое): `SetStockConfirmedOrderStatusCommandHandler.cs:22` и `SetPaidOrderStatusCommandHandler.cs:22` спят по 10 с внутри открытой транзакции (`TransactionBehavior.cs:38-43`). PaymentProcessor уже «списал» деньги и опубликовал `OrderPaymentSucceeded` (`PaymentProcessor/.../Handler.cs:23,32`), статус заказа ещё `StockConfirmed`. Если за эти ~10 с клиент отменит заказ (разрешено: `Order.cs:144-145` запрещает только `Paid`/`Shipped`) — статус станет `Cancelled`; затем `SetPaidStatus` тихо ничего не делает (`Order.cs:119-128`, условие `StockConfirmed`), а `SaveEntitiesAsync` возвращает `true` (`SetPaidOrderStatusCommandHandler.cs:30-31`). Итог уже сейчас: деньги списаны, заказ отменён, возврата нет. С новой функцией нужно: в обработчике `OrderPaymentSucceeded`, если заказ уже `Cancelled`, инициировать возврат; и/или запретить отмену в `StockConfirmed` без возврата. Аналогично для `AwaitingValidation` (остатки подтверждаются позже).
- Порядок «оплачен -> отменён» для остального мира: `Paid` и `Cancelled` события уходят в разные routing key, но в одну очередь потребителя (`RabbitMQEventBus.cs:25,258,281`), порядок внутри очереди сохраняется только если оба события опубликованы по очереди; при сбое публикации `Paid` (см. `PublishedFailed`) Catalog не спишет остатки, а затем отмена вернёт их -> остаток завышен. Возвращать нужно ровно то, что реально списано.
- Возврат остатков несимметричен: `RemoveStock` при остатке 0 бросает исключение (`CatalogItem.cs:25-28`), поглощаемое шиной (`RabbitMQEventBus.cs:170-180`) -> часть заказа не списывается вообще; кроме того, спишет «не больше, чем есть» (`CatalogItem.cs:35-37`, возвращается фактически списанное число, а событие несёт желаемое `Units`). `AddStock` ограничен `MaxStockThreshold` (`CatalogItem.cs:51-57`). Итого после «оплатить -> отменить» остаток может не вернуться к исходному. Нужно решение: возвращать «желаемое» количество, считать фактически списанное, или принять потери.
- Повтор/дубль события отмены в Catalog: обработчик Paid не идемпотентен (нет учёта обработанных событий), то же будет у обработчика возврата остатка: повтор `Cancelled` вернёт остаток дважды. Нужна дедупликация по `Id` события или по `OrderId`.
- Возврат vs отгрузка после запроса возврата: после перехода в «возврат в процессе» отгрузка должна быть запрещена (`SetShippedStatus` требует `Paid`: `Order.cs:132-135`, но новый промежуточный статус нужно учесть, иначе отгрузка и возврат пересекутся).
- Грейс-период: заказ в `Submitted` может одновременно уйти в `AwaitingValidation` (`SetAwaitingValidationStatus`, `Order.cs:99-106`) и быть отменён; `GracePeriodConfirmed` повторяется каждые 30 с, пока статус `Submitted` (`GracePeriodManagerService.cs:50-60`); после отмены статус не `Submitted`, повторы прекращаются — безопасно.
- Повторная отмена: у `SetCancelledStatus` нет защиты от `Cancelled -> Cancelled` (`Order.cs:142-153`): повторный вызов с другим `x-requestid` создаст ещё одно событие `OrderStatusChangedToCancelled` и (после доработки) ещё один запрос возврата — двойной возврат. Требуется явный запрет/идемпотентность по `OrderId`.
- Отмена при отсутствии `BuyerId`: `OrderCancelledDomainEventHandler.cs:28` и аналогичные берут `order.BuyerId.Value` — NRE, если покупатель ещё не привязан.

Обратная совместимость и данные в полёте:
- Старые мобильные клиенты ждут только `Submitted` для отмены и `400` для «статус изменился» (`OrderService.cs:102-107`), `500` приведёт к исключению; новая серверная логика не должна менять смысл существующих кодов без обновления клиента.
- Новые статусы строки: клиенты, завязанные на значения (`OrderDetailViewModel.cs:38`, CSS `.status.paid/.cancelled`, `Orders.razor.css:125-136`), покажут неизвестный статус без стилей; для WebApp копия события использует `string` (`WebApp/.../OrderStatusChangedToCancelledIntegrationEvent.cs:8`), в Ordering — `enum` с `JsonStringEnumConverter` (`OrderStatus.cs:5`), добавление значений в сериализации безопасно, но обратный порядок раскатки (старый подписчик с `enum`) может не десериализовать неизвестное значение — копии с enum есть только в Ordering.
- Заказы в полёте на момент выкладки: уже `Paid`, но без сохранённой ссылки на платёж (поля появятся новыми колонками, у старых строк они пустые) — для них возврат невозможен без fallback (возврат по `OrderId` и сумме `GetTotal()`).
- Сумма возврата и скидки: `GetTotal()` игнорирует `Discount` (`Order.cs:185`), а `OrderItem` её хранит (`OrderItem.cs:15,39`); при расхождении «списано» и «возвращаем» возможен перерасчёт — зафиксировать правило (возврат = то, что показывает `Total` в API).
- PaymentProcessor stateless и без БД: после рестарта нет памяти о платежах; идемпотентность возврата должна обеспечиваться ключом `OrderId`, хранящимся в Ordering.
- Конфиг `PaymentSucceeded` читается через `IOptionsMonitor` (`PaymentProcessor/.../Handler.cs:21`) — переключение «успех/ошибка» на лету; для возврата сделать аналогичный отдельный флаг.
- Утечка данных: `CancelOrderCommand` логируется целиком (`OrdersApi.cs:34-39`, `IdentifiedCommandHandler.cs:79-84`); не добавлять в команду платёжные реквизиты.
- Проверка прав: отсутствие проверки владельца (разд. 2) становится уязвимостью с денежным последствием.
