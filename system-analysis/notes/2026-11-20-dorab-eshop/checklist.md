# Чек-лист влияния (из эталонов A-code и B-code)

Пункт засчитывается, если план по спекам называет факт или явно учитывает его в решении (не обязательно с теми же словами).
«Частично» — упомянут, но неверно или как догадка без последствий для плана.

## A — отмена после оплаты с возвратом
A1. Событие успешной оплаты несёт только OrderId: в заказе нет ссылки на платёж и суммы, у PaymentProcessor нет хранилища — для возврата их нужно добавить.
A2. Гонка: SetPaid / SetStockConfirmed спят 10 с внутри транзакции — отмена в этом окне при уже списанных деньгах.
A3. Неудачная команда «сжигает» x-requestid (IdentifiedCommandHandler): повтор с тем же ключом отвечает 200, ничего не делая.
A4. Одна команда отмены обслуживает и покупателя, и автоотмену по отказу оплаты — причины надо разделить.
A5. Outbox не повторяет неотправленное, шина подтверждает сообщение при ошибке, DLX нет.
A6. Возврат остатка на склад несимметричен: Catalog списывает только по Paid, обрезка по MaxStockThreshold / исключение при нуле.
A7. Мобильный клиент (ClientApp): кнопка отмены только для Submitted, ловит только 400, а сервер отдаёт 500.
A8. У заказа нет токена конкурентности: cancel против ship — последняя запись побеждает.
A9. Нет проверки владельца заказа при отмене.
A10. Вебхуков на отмену нет: получатель OrderPaid не узнает об отмене.
A11. Мобильный BFF / YARP-маршрут /api/orders в AppHost.
A12. Контракт отмены: тело { orderNumber }, 400 при пустом x-requestid, 500 ProblemDetails при отказе.

## B — вес товара
B1. PUT товара заменяет все поля: клиент, не знающий о весе, его сотрёт.
B2. Создание товара и засев копируют поля вручную (CreateItem, CatalogContextSeed) — вес потеряется молча; catalog.json (~101 запись) / CatalogSourceEntry.
B3. Корзину (Basket.API, proto) менять не надо; вес берётся из каталога при оформлении (BasketState).
B4. Цепочка маппинга в Ordering: BasketItem → OrderItemDTO / FromOrder → AddOrderItem (оба вызова).
B5. Общий компонент WebAppComponents (CatalogItem / карточка) → меняется и HybridApp.
B6. JSON товара уходит в промпт ИИ-ассистента (ChatState) / эмбеддинги.
B7. В Catalog.API валидация не подключена — правило на вес нужно писать явно.
B8. Снимок миграций Ordering расходится с моделью — новую миграцию нужно просмотреть.
B9. Слияние одинаковых позиций в заказе сохраняет данные первой позиции.
B10. Мобильный клиент (ClientApp) — своя копия CatalogItem.
B11. Засев только при пустой таблице — для существующей БД нужна миграция данных.
B12. События изменения товара (ProductPriceChanged) вес не несут, при правке только веса не публикуется ничего.
