# Impact: отмена заказа после оплаты (cancel-after-payment)

Работа велась только по спекам и system-context, кода не было. Всё, что помечено «(угадано)», в материалах не подтверждено.

## 1. Затронутое поведение
Меняется:
- order-management «Отмена заказа»: Paid больше не отказ, а переход в новый статус AwaitingRefund (угадано: отдельный промежуточный статус); Shipped по-прежнему отказ (500).
- order-management «Доступ к операциям заказа»: для cancel вводится проверка владельца (сейчас её нет, Q-055); для ship и GET не меняем.
- Граф статусов (domain.md): добавляются Paid → AwaitingRefund → Cancelled. Убирается запрет Paid → Cancelled (Order.cs:144-148) только для пользовательской отмены.
- order-payment: PaymentProcessor получает вторую обязанность (возврат), сейчас только платёж (заглушка, Q-064).
- catalog-stock: остаток, списанный при Paid, должен вернуться.
- storefront: появляется кнопка отмены (сейчас вызова отмены в витрине нет вообще, ordering-api «кто их вызывает, в коде не найдено»).

Сохраняется, но опирается:
- «Отказ оплаты отменяет заказ» (order-payment) использует тот же CancelOrderCommand/SetCancelledStatus и ДОЛЖЕН и дальше отклонять Paid/Shipped: нельзя просто снять запрет в Order.cs:144-148, иначе событие «оплата не прошла» начнёт отменять оплаченный заказ без возврата. Нужен отдельный путь.
- «Повтор запроса с тем же x-requestid» (IdentifiedCommandHandler, RequestManager): неудачные попытки тоже запоминаются, повтор с тем же id отвечает 200 без действия (Q-058). Для денег критично: ретрай клиента после сбоя «молча успешен».
- «Повторная отмена отменённого заказа» (Q-059) публикует событие повторно; для возврата это нельзя копировать.
- «Событие о смене статуса уходит после фиксации транзакции» (TransactionBehavior.cs:32-53).
- «Оплата переводит заказ в Paid через 10 с» (SetPaidOrderStatusCommandHandler.cs:22): окно, где платёж идёт, а заказ ещё StockConfirmed.
- Q-060: отмена до оплаты не ограничена периодом ожидания.

## 2. Контракты API
HTTP (Ordering.API, версия 1.0):
- `PUT /api/orders/cancel` (OrdersApi.cs:11, :22-49). Заголовок `x-requestid` (GUID, непустой), тело — номер заказа (имя поля в спеке не указано, угадано: `orderNumber`).
  - Было: 200 для статусов до Paid; 500 «Cancel order failed to process.» для Paid/Shipped; 400 при пустом GUID.
  - Станет: 200 для Paid (заказ уходит в AwaitingRefund, фактический возврат асинхронно); 500 для Shipped и AwaitingRefund; чужой заказ — отказ (403, угадано).
  - Совместимость: ответ 200 теперь НЕ означает «заказ отменён» — только «принято»; клиенты, считающие 200 = Cancelled, ломаются. Появляется новое значение статуса в `GET /api/orders` и `GET /api/orders/{id}` (поле статуса — строка): потребители с закрытым списком статусов ломаются (витрина, внешние).
- `GET /api/orders`, `GET /api/orders/{orderId}`: новое значение статуса `AwaitingRefund`. Структура не меняется. Нужен ли признак «возврат» в ответе — не знаю (угадано: нет).
- gRPC: не затрагивается (корзина).
- Новых HTTP-входов в Ordering нет; PaymentProcessor сейчас не имеет HTTP-входов в материалах.

## 3. События

- Новое: запрос возврата. Имя (угадано): `OrderStatusChangedToAwaitingRefundIntegrationEvent` (по шаблону OrderStatusChangedTo*). Поля (угадано): OrderId, OrderStatus, BuyerName, сумма заказа, позиции. Публикует Ordering.API после фиксации транзакции; подписан PaymentProcessor (подписка в src/PaymentProcessor/Program.cs:6) — вызывает возврат. Подписаны также WebApp (перезагрузка списка, src/WebApp/Extensions/Extensions.cs:45-50, новый обработчик).
- Новое: `OrderRefundSucceededIntegrationEvent` / `OrderRefundFailedIntegrationEvent` (угадано, по шаблону OrderPaymentSucceeded/Failed). Поле OrderId. Публикует PaymentProcessor напрямую в шину БЕЗ журнала событий (как оплата, spec «Результат оплаты теряется при сбое публикации», Q-049). Подписан Ordering.API (Extensions.cs:57-61).
- Новое: возврат остатка. Имя (угадано): `OrderStockReturnedIntegrationEvent` (OrderId, позиции: ProductId, Units). Публикует Ordering.API при AwaitingRefund → Cancelled; подписан Catalog.API (рядом с Extensions.cs:31-33), увеличивает остаток.
- Меняется использование: `OrderStatusChangedToCancelled` теперь публикуется ещё и после возврата (подписчик WebApp; Webhooks.API не подписан). Текущая отмена по складу событие не публикует (Q-051).
- `OrderStatusChangedToPaid`: подписчики Catalog (списание), WebApp, Webhooks.API (OrderPaid). Отмена после оплаты НЕ откатывает их эффект: внешние получатели вебхука получили OrderPaid и об отмене не узнают (Q-096, webhook-delivery «Смена…», рассылка отмены отсутствует).
- Порядок/повтор: подписчики не идемпотентны (в материалах идемпотентности входящих событий нет).

## 8. Риски
- Деньги и потеря событий: запрос возврата и его результат идут по шине без повторов и DLX (Q-049); PaymentProcessor публикует вне журнала (Q-049, Q-054). Потеря любого — заказ навсегда «Ожидает возврата», деньги не возвращены/неизвестно. Нужен хотя бы фоновый повтор по статусу (как OrderProcessor) — не заложено.
- Идемпотентность: x-requestid запоминается даже при неудаче (Q-058); событие запроса возврата может прийти дважды — двойной возврат. Событие возврата остатка дважды — двойное восстановление остатка.
- Гонка «отмена vs оплата»: пользователь отменяет в StockConfirmed, пока идёт 10-секундная пауза; «оплата прошла» тихо игнорируется для Cancelled (Q-061). С реальным шлюзом деньги были бы списаны без заказа — нужен возврат и в этом случае. Обратная: отмена Paid в момент отгрузки (Paid → Shipped, ship без проверки роли, Q-055).
- Гонка «отмена vs ship»: параллельные Cancel и Ship для Paid; нужна оптимистичная блокировка/транзакция — механизм в материалах не описан.
- Частичная неатомарность: переход статуса и публикация события не атомарны (событие после коммита, Q-054/Q-076): статус AwaitingRefund записан, событие потеряно.
- Остаток: списание при Paid срезает до нуля (Q-029), отмена вернёт больше, чем списали; нет резерва (Q-030). Возможна «лишняя» единица на складе.
- Безопасность: проверка владельца при cancel; но get/ship остаются без неё (Q-055). Токен принимается любой (Q-001).
- Обратная совместимость: новый статус в ответах API; внешние клиенты (maui, получатели) могут не знать значение. OrderCancelledDomainEvent публикует Cancelled для WebApp по идентификатору покупателя — новое событие после возврата должно нести его (OrderCancelledDomainEventHandler.cs:30).
- Данные в полёте: заказы в Paid на момент выката — отмена к ним применима сразу. 10-секундные паузы Ordering (Q-053) удлиняют цепочку.
- Вебхуки: получатели видели OrderPaid и не увидят отмену — расхождение учёта партнёров.
- Персональные/платёжные данные: карта фиксирована (Q-064); данные карты в журналах (Q-035) — возврат не должен добавлять новых утечек.
