Системный анализ · sa-scan

sa-scan: как сервис работает сейчас — в спеках и карте системы

Скилл читает готовый репозиторий и снимает с кода мастер-спецификацию OpenSpec «как есть», карту системы для агентов и чек-лист вопросов о внешнем мире. Дальше агенты дорабатывают проект по спекам (SDD), не ломая то, о чём не знали.

Что даёт

Агент, который завтра делает фичу, получает не «прочитай весь код», а готовые ответы: что система делает, где это в коде, кто ещё на это опирается и что пока неизвестно.

Спеки «как есть», с багами

openspec/specs/<возможность>/spec.md: требования SHALL/MUST и сценарии WHEN/THEN по коду. Странное поведение не «чинится» в спеке, а помечается и уходит вопросом.

Карточка изменения на возможность

system-context/caps/<id>.md на ~3 тыс. токенов: требования с кодом, входы и ответы, события, кто ещё вызывает, данные, блокирующие вопросы. Это то, что откроет агент на слабой модели.

Контракты и вызывающие

contracts.md: поля запросов и событий, коды ответа, кто публикует и подписан, какие клиенты и шлюзы вызывают вход и на что опираются (например, «кнопка отмены только для Submitted»).

Данные

data.md: сущности, где создаются, куда копируются поля (DTO, модели клиентов), миграции и засев, нет ли защиты от гонок, где не подключена валидация.

Вопросы о внешнем мире

QUESTIONS.md: всё, что не прочитать из репозитория (прод, партнёры, «баг или так задумано»), с допущением, на котором держится спека. В чат — 5–7 главных.

Требование → код и тесты

trace.md: где в коде каждое требование и какие тесты его проверяют. По нему же GUIDE.md строит карту параллельной работы: какие изменения можно раздать агентам одновременно.

Когда звать

Скилл нужен один раз при переводе проекта на агентную разработку и потом — для обновления слоя.

Подходит

  • Есть работающий сервис или монорепо, и его хотят вести по спекам (OpenSpec, SDD).
  • Нужно описать, как система работает на самом деле, и сверить код с PRD или ТЗ.
  • Агенты будут дорабатывать большой репозиторий, и им нужна карта: кто кого вызывает, где данные, что неизвестно.
  • Код поменялся, слой устарел — режим «обновить после изменений кода».

Не подходит

  • Новая фича по готовой спеке — это работа по openspec/changes/, а не съёмка «как есть».
  • Дизайн интерфейса — это wd-scan.
  • Проект пустой или из одного файла: спека дороже самого кода.

Что дальше

Слой не разовый: по нему работают, его дополняют ответами и обновляют после изменений кода.

Снять «как есть»

Режим A: спеки, карта, вопросы.

sa-scan · этот скилл
→

Ответить на вопросы

Человек отвечает, режим B вносит: ошибки кода → предложения в openspec/changes/.

→

Дорабатывать по спекам

Агент берёт карточку, пишет change-proposal, реализует, архивирует изменение — спека обновляется.

sa-change · в планах
→

Следить за расхождением

Новые и исчезнувшие входы, правки в обход changes/, устаревшие строки.

sa-drift · в планах
→

A · Снять спеку

Когда: первый проход по проекту

Шаги 1–9. На большом репо (~8+ возможностей) и когда важна полнота — режим раздачи по субагентам: глубже, но в несколько раз дороже.

B · Внести ответы

Когда: «я ответил в QUESTIONS.md»

Три исхода ответа. Слой прежней версии сначала достраивается: contracts.py scan, plan.py guide.

C · Обновить после кода

Когда: «код поменялся, обнови»

Пересканировать опись и контракты (заметки вне блоков сохраняются), разложить новые входы, переписать затронутые спеки.

Как результат используется потом

Агент доработки

AGENTS.md → GUIDE.md → карточка возможности → при необходимости grep по contracts.md. Меняет поведение через openspec/changes/.

Человек (владелец продукта)

Отвечает на вопросы в QUESTIONS.md, ревьюит предложения изменений, видит, где код расходится с PRD.

Тимлид

Раздел «Параллельная работа» в GUIDE.md: какие возможности делят код и какими волнами раздавать задачи агентам без конфликтов.

Главные правила

Почему скилл ведёт себя так, а не иначе.

  • Как есть, с багами.На спеку будут опираться при изменениях; «исправленная» в спеке ошибка станет невидимой. Исправление — отдельное изменение в openspec/changes/.
  • Расхождение кода и документа — всегда вопрос.Не выбирать молча ни код, ни PRD: в спеке — код, в вопросе — обе версии со ссылками.
  • Внешний мир — вопросом, а не догадкой.Контракты партнёров, значения в проде, кто ещё вызывает API — не читаются из репозитория. Догадка без пометки станет «требованием».
  • Требование называет вход, но не класс.«По запросу PUT /api/orders/cancel» — это контракт, его агент ищет по задаче. Файлы и классы — в trace.md.
  • Клиент в репо — потребитель контрактов.Мобильное приложение или SPA можно исключить из входов, но не забыть: их ожидания (статусы, коды ответа) ломаются первыми.
  • Только чтение снаружи, секреты — только имена.Скилл не вызывает внешние API и не читает значения .env.
