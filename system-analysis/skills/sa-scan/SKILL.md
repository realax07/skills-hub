Не для новой фичи по готовой спеке и не для дизайна интерфейса (это wd-scan).

# sa-scan

Первый шаг аналитики при переводе готового проекта на агентную разработку. Скилл снимает с кода **как сервис работает сейчас**
и раскладывает это так, чтобы дальше агенты работали по SDD (spec-driven development) в OpenSpec:
- `openspec/specs/<возможность>/spec.md` — требования и сценарии: поведение, без деталей реализации;
- `system-context/` — то, чего в спеке быть не должно, но без чего агент не начнёт: опись входов, внешние системы, сущности и статусы,
  роли, глоссарий, связь «требование → код и тесты», **контракты и данные** (поля, события, кто ещё вызывает вход, куда копируются поля)
  и **открытые вопросы** — всё, что не понять из одного репозитория.

Нужен только Python 3.9+ (стандартная библиотека). CLI OpenSpec необязателен: если он есть в PATH, проверка запускает и `openspec validate --strict`.

Код — источник «как есть», человеческая спека — источник «как задумано». Расхождение между ними не решается молча:
спека пишется по коду, с пометкой `(допущение: Q-…)`, а вопрос уходит человеку.

## Как выполнять

Для любой модели: запускай команды как написано, `<skill>` — папка этого скилла, `<repo>` — корень репозитория проекта.
Пиши команду целиком, а не через переменную (`P="python3 …"; $P` в zsh не работает); повторяешь много раз — сделай функцию оболочки.
У каждого скрипта есть `--help`; не придумывай флаги. Скрипт упал — смотри «Если что-то не так», не обходи вручную.
Файлы плана и вопросов правь только скриптами (`plan.py`, `questions.py`): так не собьются формат и нумерация.

Три режима — выбери по запросу:
- **A. Снять спеку** — первый проход (шаги 1–9). По умолчанию.
- **B. Внести ответы** — человек ответил на вопросы («я ответил в QUESTIONS.md», «вот ответы: …») — раздел «Режим B».
- **C. Обновить после изменений кода** — «код поменялся, обнови» — раздел «Режим C».

## Режим A: снять спеку

1. **Входные данные.** Пользователь рядом — спроси одним сообщением то, чего нет в запросе. Автономный прогон («меня не будет», некому ответить) —
   не спрашивай, бери умолчания из последнего пункта списка ниже.
   - **Репозиторий:** корень проекта. Монорепо — один `openspec/` в корне, возможности по сервисам.
   - **Человеческая спека:** PRD, ТЗ, Confluence, вики — файлы или ссылки. Закрытая ссылка (нужен вход) — попроси выгрузить в файлы;
     в репозиторий их не клади без согласия: внутренние документы бывают конфиденциальны. Нет спеки — работай по коду.
   - **Язык спек** (по умолчанию — язык пользователя) и **куда вписать указатель**: `python3 <skill>/scripts/link.py <repo> --suggest`.
   - **Стенд** (необязательно): адрес тестового окружения — только для чтения, чтобы проверить поведение. Прод и чужие API не трогай.
   - **Спросить некого** (автономный прогон): спеки нет — только код; язык — язык запроса; все вопросы — в файл;
     указатель — в найденный файл инструкций (`AGENTS.md` в приоритете), а если их нет — создай `AGENTS.md`: без указателя агенты
     не найдут слой, а новый файл ничего не ломает. Не трогай файлы инструкций, только если пользователь так сказал.

2. **Опись.** `python3 <skill>/scripts/inventory.py scan <repo>` → `system-context/inventory.md` и `inventory.json`.
   Прочитай `inventory.md` целиком: стек, входы, внешние хосты и SDK, переменные окружения, сущности и статусы, проверки прав, тесты, документы, TODO.
   Выборка, если файл большой: `inventory.py show <repo> --kind http --grep orders` (`--section outbound|env|entities|tests|todos|authz`).
   Опись — эвристики: найденное проверяй по коду, пропущенное добавишь на шаге 4. Уже есть `openspec/` — [rules.md](references/rules.md#если-openspec-уже-есть).

3. **Человеческая спека.** Прочитай каждый источник и выпиши для себя утверждения, которые можно проверить кодом:
   лимиты, сроки, роли, статусы, правила («до 30 позиций», «отмена через час»). Это список для сверки на шаге 5.

4. **План возможностей.**
   - `python3 <skill>/scripts/plan.py init <repo> --source <файл-или-URL> [--source …] --language ru` — черновой план из описи
     и заготовки `system-context/`, `openspec/`. Черновые группы — по путям и папкам, это не возможности.
   - `plan.py status <repo>` → преврати группы в **возможности по поведению пользователя или бизнеса** (`order-checkout`, а не `orders-controller`):
     `plan.py rename <repo> <cap> <new> --title "…"`, `plan.py add-cap <repo> <cap> --title "…"`, `plan.py merge <repo> <из> <в>`,
     `plan.py move <repo> "<шаблон>" <cap>`. Шаблон — id из описи с видом в начале (`"http:GET /documents"`) или с `*` (`"http:* /documents*"`).
     Как резать — [rules.md](references/rules.md#возможности); обычно 5–15 на сервис.
   - Каждый вход — в возможность или `plan.py exclude <repo> "<шаблон>" --reason "…"` (служебное, отладка, мёртвый код — последнее ещё и вопросом).
   - Вход, которого опись не нашла (самописный роутер, редкий фреймворк), — `plan.py add-entry <repo> "<вид>:<имя>" --file <путь> --line <N> --cap <cap>`.
   - Клиент в репозитории (мобильное приложение, SPA, второй сервис) — не вход, но **потребитель контрактов**: его входы можно исключить,
     а его самого — нет: `contracts.py` найдёт, что он вызывает, и в `contracts.md` останется место «Опирается на».
   - **Контракты и данные:** `python3 <skill>/scripts/contracts.py scan <repo>` → `system-context/contracts.md` (по входу: сигнатура, заголовки,
     ответы из кода, типы с полями; события: поля, кто публикует и подписан, расхождения копий; кто вызывает входы — клиенты, шлюзы, промпты ИИ)
     и `data.md` (сущности с полями и ограничениями, где создаются, копии полей, миграции, засев, конкурентность, транзакции, валидация).
     Без этого агент доработки видит поведение, но не видит, по чему нельзя сломаться. Повторный запуск сохраняет заметки вне блоков `sa:auto`.

5. **По возможностям — цикл**, по одной; на большом репо 1–3 за проход, продолжишь по `plan.py status`.
   Умеешь запускать субагентов, возможностей ~8+ (или код не помещается в контекст) и важна полнота, а не цена — **режим раздачи** вместо цикла
   (глубже, но в несколько раз дороже по токенам):
   общая основа сам, брифы `plan.py brief <repo> --all`, работники по возможностям, сборка `plan.py collect <repo>` —
   [references/fan-out.md](references/fan-out.md). Иначе — цикл:
   1. `python3 <skill>/scripts/plan.py next <repo>` — входы, файлы, внешние вызовы, тесты, TODO, источники и раздел «Контракты и данные» этой возможности.
   2. Прочитай обработчики и **иди по вызовам** до БД и внешних систем: проверки, ветки ошибок, статусы, лимиты, ретраи.
      Тесты — готовые сценарии. Сверь со списком из шага 3. Ответы и поля из «Контракты и данные» сверь с кодом: исключение из глубины
      (домен, репозиторий) превращается в 500 — допиши строкой «Заметки: …» под блоком входа в `contracts.md`.
   3. Напиши `openspec/specs/<cap>/spec.md` по [assets/spec.template.md](assets/spec.template.md) и [references/openspec-format.md](references/openspec-format.md):
      `## Purpose`, требования `### Requirement:` с SHALL/MUST, у каждого сценарии `#### Scenario:` с `- **WHEN**` / `- **THEN**`.
      Требование **называет вход**, как его видит вызывающий: «по запросу PUT /api/orders/cancel», RPC `GetBasket`, событие оплаты —
      иначе агент, который меняет вход, не найдёт его требование (`check.py` предупредит).
   4. Всё, что не понять из кода (внешний сервис, прод, расхождение с документом, «баг или так задумано»), — вопрос. Порядок, чтобы не путать номера:
      требование уже в спеке (без пометки) → `python3 <skill>/scripts/questions.py add <repo> --title "…?" --category "…" --seen "… (файл:строка)" --affects "<cap> / <Требование>" --assume "…" --who "…" [--importance блокирует]`
      → номер из вывода (`✓ Q-007`) → пометка в требовании `(допущение: Q-007)`; несколько — через запятую `(допущение: Q-004, Q-006)`.
      Номера заранее не угадывай. Заголовок заканчивается «?»; имя в `--affects` — дословно как в spec.md; `--importance` по умолчанию `уточняет`;
      `файл:строка` в `--seen` сверь по коду (`grep -n`). Поправить вопрос — `questions.py edit <repo> Q-… --title/--affects/…`.
      Какие вопросы и как их формулировать — [references/questions.md](references/questions.md).
   5. В `system-context/trace.md` под `## <cap>` — строка на **каждое** требование: `- <Имя требования> → путь:строка, путь:10-20 | тесты: путь`
      (нет тестов — `| тесты: —`; пояснение — в скобках после пути: `test/x.ts (заглушка, проверяет только 422)`).
   6. `python3 <skill>/scripts/check.py <repo> --cap <cap>` — без ✗, затем `plan.py set <repo> <cap> --status done` (он сам повторит проверку и не даст done с ошибками).

6. **Карта системы** — заполни заготовки в `system-context/` (места `<!-- заполнить … -->`):
   - `integrations.md` — каждая внешняя система из описи (хосты, SDK, исходящие вызовы, вебхуки, очереди от других): направление, когда, что передаём, **что при отказе**, настройки, где в коде;
   - `domain.md` — сущности, переходы статусов «ИЗ → В: когда», таблица прав «действие × роль», бизнес-константы;
   - `glossary.md` — термины как их зовут люди и как в коде;
   - `contracts.md` — «Опирается на» у каждого вызывающего: открой его файлы и запиши, какие поля он читает, какие статусы и коды сравнивает
     (мобильный клиент показывает отмену только для `Submitted`, ловит только 400) — это ломается первым; «Что уходит в модель» — для ИИ.
     В каждом заполненном месте — факты со ссылками `путь:строка`: общие слова («использует поля заказа») `check.py` не примет;
   - `data.md` — «Что это значит» под конкурентностью и транзакциями (что защищено от гонок, что публикуется вне транзакции) и под валидацией;
   - `openspec/config.yaml` — 2–4 строки `context` о продукте (подробности — не сюда, а в `system-context/`).

7. **Гайд, карточки и указатель.** `python3 <skill>/scripts/plan.py guide <repo>` → `system-context/GUIDE.md` (с чего начать, задача → файл,
   таблица возможностей, правила, «Параллельная работа» — волны изменений без конфликтов) и **карточки** `system-context/caps/<id>.md`:
   по возможности — требования с кодом, входы с ответами, события, кто ещё вызывает, данные, общие ограничения, открытые вопросы, в бюджете
   ~3 тыс. токенов. Карточка — то, что откроет агент доработки на слабой модели: большие файлы он целиком не прочтёт. Карточки собираются
   из источников — повторяй `plan.py guide` после любых правок спек, контрактов и вопросов, руками их не правь.
   `python3 <skill>/scripts/link.py <repo> --file AGENTS.md` — блок между метками `<!-- sa-scan:start/end -->`, остальной текст не трогает.
   Claude Code читает только `CLAUDE.md`: если его нет, `link.py` создаст `CLAUDE.md` со строкой `@AGENTS.md`; если он есть и не
   подключает AGENTS.md — следуй подсказке `link.py`.

8. **Проверка.** `python3 <skill>/scripts/check.py <repo>` — готово, когда **ошибок 0**. Проверяет покрытие входов, формат спек
   (и `openspec validate --strict`, если CLI есть), трассировку и файлы, вопросы и пометки, внешние хосты и SDK в `integrations.md`, указатель.
   Затем открой `GUIDE.md` и одну спеку глазами агента, который завтра делает фичу: понятно, что менять, где и кого это заденет
   (вызывающие и подписчики в `contracts.md`, копии полей в `data.md`)?

9. **Вопросы и отчёт.** `python3 <skill>/scripts/questions.py top <repo> --n 7` — главные вопросы **в чат** (есть кому ответить — ответ впиши
   `questions.py answer` и сразу режим B), полный список — **в файле** `system-context/QUESTIONS.md`: там человек ответит позже.
   Отчёт: возможности и число требований, найденные расхождения кода и документа, внешние системы, сколько вопросов и где они,
   что исключено и почему, указатель, как дальше: изменения — через `openspec/changes/`, ответы — «внеси ответы».

## Режим B: внести ответы

Слой собран прежней версией скилла (нет `contracts.md`, `data.md` или `caps/`) — сначала дострой его: `contracts.py scan <repo>`,
заполни места «заполнить» (шаг 6), затем `plan.py guide <repo>`. Иначе `check.py` не пройдёт, а агент доработки не получит карточек.

1. `python3 <skill>/scripts/questions.py sync <repo>`, затем `questions.py list <repo> --status отвечен` — вопросы с ответом.
   Ответ пришёл в чате — сначала `questions.py answer <repo> Q-… "текст"`.
2. По каждому ответу — один из трёх исходов ([questions.md](references/questions.md#внести-ответы)):
   - **Код верен** (так и задумано) — убери пометку `(допущение: Q-…)`, поправь формулировку, если нужно;
   - **Код ошибается** (должно быть иначе) — требование **остаётся как есть** (спека описывает текущее поведение), пометку замени на
     «Известное расхождение: …, исправление — `changes/<id>`» и создай предложение изменения `openspec/changes/<id>/` по [assets/change/](assets/change/):
     `proposal.md`, `tasks.md`, `specs/<cap>/spec.md` с `## MODIFIED Requirements` (имя требования — дословно, все его сценарии — с теми же именами);
   - **Новые сведения** (контракт, значения в проде) — уточни требование и сценарии, `integrations.md`, `domain.md`; пометку убери.
     Сценарии описывают, что делает **наша** система (контракт партнёра — в `integrations.md`).
3. `questions.py set <repo> Q-… --status внесён` (скрипт не даст закрыть, пока пометка осталась в спеке). Вопрос не актуален — `--status снят --note "почему"`.
4. Ответ породил новый вопрос (ответ расходится с кодом) — `questions.py add`, пометка с новым номером — на то же требование.
   `trace.md` правь, только если изменились ссылки на код. Затем `plan.py guide <repo>` и `check.py <repo>` — без ✗. Отчёт: что поправлено, какие изменения предложены.

## Режим C: обновить после изменений кода

Нет `contracts.md`, `data.md` или `caps/` — дострой, как в начале режима B.

`inventory.py scan <repo>` → `plan.py status <repo>`: исчезнувшие входы — `plan.py prune <repo>`, новые — `move` в возможности
(или новая возможность) → `contracts.py scan <repo>` (блоки обновятся, заметки останутся; исчезнувшее помечено ⚠) → цикл шага 5
для затронутых → `plan.py guide`, `check.py`. Изменения, внесённые через `openspec/changes/` и архивированные,
спеку уже обновили — проверь только трассировку.

## Ключевые правила

- **Как есть, с багами.** Спека описывает текущее поведение, даже странное: на неё будут опираться при изменениях, и «исправленная» в спеке ошибка
  станет невидимой. Подозрение на ошибку — вопрос «баг или так задумано» и пометка, исправление — отдельное изменение в `changes/`.
- **Расхождение кода и документа — всегда вопрос.** Не выбирай молча ни код, ни PRD: в спеке — код, в вопросе — обе версии со ссылками.
- **Внешний мир — вопросом, а не догадкой.** Контракты, SLA, значения флагов в проде, кто ещё вызывает API — не читаются из репозитория.
  Пиши по разумному допущению, помечай и спрашивай: иначе догадка станет «требованием», и агент будет на неё опираться.
- **Требование — наблюдаемое поведение.** Без файлов, классов и библиотек — они в `trace.md`. Одно поведение — одно требование до 500 символов,
  у каждого хотя бы один сценарий, лучше два: обычный и отказ или граница.
- **Ключевые слова OpenSpec — по-английски.** Заголовки `## Purpose`, `### Requirement:`, `#### Scenario:`, слова SHALL/MUST и WHEN/THEN разбирает CLI;
  текст — на языке проекта.
- **Секреты и персональные данные — только имена.** Значения из `.env` не читай и не переписывай; персональные данные отмечай категорией.
- **Только чтение снаружи.** Не вызывай внешние API, вебхуки и прод, чтобы «проверить»: побочные эффекты реальны. Стенд — только с разрешения и без изменений данных.
- Подробно — [references/rules.md](references/rules.md).

```
  changes/<id>/                  (режим B) предложения исправлений: proposal.md, tasks.md, specs/<cap>/spec.md (дельта)
system-context/
  GUIDE.md                       вход для агента: с чего начать, задача → файл, возможности, правила, параллельная работа
  caps/<id>.md                   карточка изменения по возможности (~3 тыс. токенов) — собирает plan.py guide, руками не править
  QUESTIONS.md                   чек-лист и открытые вопросы с допущениями и полем «Ответ»
  trace.md                       требование → код и тесты
  integrations.md                внешние системы: направление, когда, данные, отказы, настройки
  contracts.md                   входы и события: поля, ответы, кто публикует и подписан; кто вызывает входы и на что опирается
  data.md                        сущности, где создаются и куда копируются поля, миграции, засев, конкурентность, транзакции, валидация
  domain.md                      сущности, статусы и переходы, роли и права, бизнес-константы
  glossary.md                    термины: люди ↔ код
  inventory.md, inventory.json   опись входов, выходов, env, данных, тестов (служебное, для режима C)
  contracts.json                 то же, что contracts.md и data.md, для скриптов (служебное)
  plan.json                      возможности и входы (служебное)
AGENTS.md                        блок-указатель <!-- sa-scan:start/end -->
```

Всё это — слой контекста для агентов: держи его в git (не в `.gitignore`). Коммить сам — только если пользователь просит. Объём: спека возможности — 1–4 тыс. токенов, `GUIDE.md` — до 2 тыс.

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `inventory.py`: «входы: 0 — стек не распознан» | фреймворк не из списка: найди точки входа по коду (роутинг, main, обработчики) и добавь `plan.py add-entry`; это не повод сдаться |
| в описи явно лишнее (клиентский `axios.get('/x')` во фронтенде как маршрут, тестовый сервер) | `plan.py exclude "<шаблон>" --reason "клиент, не вход"` |
| маршрут без префикса (`GET /` вместо `/api/orders`) | префикс задаётся там, где опись не видит (конфиг, фабрика) — проверь по коду, имя входа не важно: важно, что он отнесён к возможности; путь в спеке пиши настоящий |
| `check.py`: «вход … есть в плане, но нет в описи» | после пересканирования id сменился: `plan.py prune <repo>`, затем новые id — `move` |
| `check.py`: «нет SHALL или MUST» | ключевое слово по-английски заглавными внутри русского текста: «Система SHALL …» |
| `check.py`: «нужны шаги WHEN и THEN» | шаги — строками списка `- **WHEN** …`, `- **THEN** …` сразу под `#### Scenario:` |
| `check.py`: «внешний хост … не описан» | опиши систему в `integrations.md`; если это не интеграция (ссылка в письме, документация) — строкой в «Инфраструктура» с пояснением |
| `check.py`: «MODIFIED заменяет требование целиком — перенеси и сценарии» | в дельту — все сценарии текущей версии с теми же именами, текст поправь под новое поведение |
| `check.py`: «… без ссылки путь:строка» | открой файлы раздела и запиши факты со ссылками: какое поле, какой статус, что сломается |
| `check.py`: «нет карточек» или «карточки старше …» | `plan.py guide <repo>` — карточки пересобираются из спек, контрактов и вопросов |
| `check.py`: «входы не названы ни в одном требовании» | впиши метод и путь (RPC, страницу) в текст требования или шаг сценария; путь с параметром — как в коде: `/api/orders/{id}` |
| `contracts.md`: у типа «полей не найдено», ответов нет | эвристика не разобрала: открой определение и допиши строкой «Заметки: …» под блоком; блок руками не правь — перепишется |
| `check.py`: «нет разделов для N входов» или «больше не найдено» | опись новее: `contracts.py scan <repo>`; исчезнувший раздел удали вместе с заметками |
| `check.py`: «правило с «: » без кавычек» | возьми правило в `config.yaml` в двойные кавычки |
| `questions.py set … внесён`: «ещё упоминается в спеках» | сними пометку `(допущение: Q-…)` в указанной спеке, поправь требование |
| `openspec validate` ругается, а свой разбор — нет | верь CLI: правь по его сообщению; формат CLI мог измениться — сверь с [openspec-format.md](references/openspec-format.md) и openspec.dev |
| в `openspec/specs/` уже есть спеки, не от этого скилла | не перезаписывай: [rules.md](references/rules.md#если-openspec-уже-есть) |
| репозиторий огромный, контекста не хватает | по 1–3 возможности за проход; `plan.py next` даёт только нужные файлы; опись читай выборками `inventory.py show` |

## Пример

**Запрос:** «Переводим orders-service на агентную разработку. Сними спеку для OpenSpec, PRD в docs/prd.md».
**Ход:** опись (7 HTTP, вебхук Stripe, очередь отгрузки, cron) → план: 5 возможностей → спеки по циклу → 8 вопросов
(4 расхождения с PRD: лимит позиций 50 против 30, автоотмена 30 мин против 1 ч, цена из запроса против каталога, кто отменяет оплаченный) →
карта, гайд, указатель → `check.py`: 0 ошибок → 7 главных вопросов в чат, остальное в `QUESTIONS.md`.

- [examples/01-orders-service.md](examples/01-orders-service.md) — полный проход: план, спека, вопросы, трассировка
- [examples/02-requirements-bad-good.md](examples/02-requirements-bad-good.md) — плохо/хорошо: требования, сценарии, вопросы
- [examples/03-apply-answers.md](examples/03-apply-answers.md) — режим B: три исхода ответа, предложение изменения
