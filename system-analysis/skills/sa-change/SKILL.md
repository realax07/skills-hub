# sa-change

Второй шаг аналитики: изменение планирует системный аналитик, код пишут dev-агенты. Скилл превращает просьбу
(«покупатель может отменить оплаченный заказ») в пакет OpenSpec, по которому dev-агент, даже на слабой модели, сделает всё
и ничего не сломает: какое поведение меняется, кого это заденет, где новое поле надо добавить руками, что ещё неизвестно,
какие задачи в каком порядке и как проверить.

Опирается на слой sa-scan: карточки возможностей, контракты и вызывающих, данные, вопросы, трассировку. Без слоя влияние не посчитать —
сначала sa-scan. Нужен только Python 3.9+; CLI OpenSpec необязателен (если есть — проверка запускает `openspec validate`).

## Как выполнять

Для любой модели: шаги по порядку, команды как написано (`<skill>` — папка этого скилла, `<repo>` — корень проекта).
У скрипта есть `--help`; флаги не придумывай. Скрипт упал — смотри «Если что-то не так». Код проекта не меняй: только `openspec/changes/<id>/`.

## Процесс

1. **Слой.** `python3 <skill>/scripts/change.py layer <repo>` — слой на месте и свежий? Есть ли `design-context/`, `test-cases/`,
   активные изменения. Слоя нет — скажи пользователю и предложи sa-scan; «слой мог устареть» — сверяй затронутое с кодом и скажи об этом в отчёте.

2. **Просьба.** Выпиши, что меняется в поведении, для кого, что точно не меняется. Неясно главное (какие статусы, кто может, что при ошибке) —
   спроси пользователя одним сообщением. **Спросить некого** — прими допущения, запиши их в proposal («Открытые вопросы») и в отчёт.

3. **Что затронуто.** `change.py find <repo> --text "<слова задачи>"` — возможности, входы, события, сущности по словам.
   Открой карточку каждой кандидатки `system-context/caps/<id>.md` и реши: какие возможности **меняются** (поведение в их спеке станет другим),
   какие входы, события и сущности (их поля) трогаешь. Задача про несколько возможностей — это нормально.

4. **Заготовка и влияние.**
   - `change.py new <repo> <id> --title "<название>"` — `openspec/changes/<id>/` с proposal, design, tasks. id — kebab-case по смыслу: `cancel-paid-order`.
   - `change.py analyze <repo> <id> --cap <возможности через запятую> [--entry "<id входа>"] [--event <имя>] [--entity <Сущность>]`
     → `impact.md`: пункты влияния — вызывающие и на что они опираются, подписчики событий, места создания и копии полей сущности,
     засев, промпты ИИ, миграция, блокирующие вопросы, тест-кейсы, проверка интерфейса; плюс тесты и файлы затронутых возможностей.
     Меняешь поле сущности — `--entity` обязательно: иначе места, где поле потеряется молча, не попадут в план.

5. **Дельты спек** — `specs/<cap>/spec.md` на каждую меняющуюся возможность ([references/rules.md](references/rules.md#дельты)):
   - новое поведение — `## ADDED Requirements`; изменённое — `## MODIFIED Requirements`: возьми требование целиком
     `change.py req <repo> <cap> "<Имя>"`, вставь и правь текст; **все сценарии оставь** с теми же именами (CLI иначе потеряет их);
   - требование называет вход («по запросу POST /api/orders/{id}/cancel»), SHALL/MUST, у каждого — сценарий WHEN/THEN, лучше два (обычный и отказ);
   - поведение по блокирующему вопросу — по допущению с пометкой `(допущение: Q-…)`, сам вопрос — в proposal.

6. **proposal.md и design.md** — по заготовкам. В proposal **«Влияние»**: строкой на каждый пункт impact.md, что у него поменяется;
   **«Открытые вопросы»**: каждый блокирующий вопрос из impact.md и новые — что спросить, у кого, что принято до ответа.
   design: решения с причинами, данные и контракты «было → стало» (поля, коды, совместимость), миграция данных, риски, проверка.

7. **tasks.md — для dev-агента** ([правила задач](references/rules.md#задачи)): по задаче на место в коде, у каждой — файл или `Класс.Метод`
   и «готово, когда» (требование, сценарий или тест). Задача — до ~2 часов работы. Разделы заготовки: данные и контракты → поведение →
   вызывающие и подписчики → проверка → слой контекста (обновить trace.md и пересобрать слой — уже в заготовке).
   Каждое ADDED/MODIFIED требование названо в какой-то задаче по имени.

8. **Решения в impact.md.** У каждого пункта строка **Решение**: `задача 3.2` (номер из tasks.md) или `не затрагивается: <почему>`;
   у вопроса — `ответ: …` или `в proposal: <что принято до ответа>`. Нашёл влияние, которого нет в слое, — допиши пункт `X-01` сам.

9. **Проверка.** `change.py check <repo> <id>` — без ✗: заготовки заполнены, дельты в формате OpenSpec (и `openspec validate`),
   задачи называют требования и обновление trace.md, у каждого пункта влияния решение, задачи из решений существуют,
   блокирующие вопросы — в proposal. Затем перечитай tasks.md глазами dev-агента на слабой модели: можно ли сделать каждую задачу, ничего не угадывая?

10. **Несколько изменений сразу** — `change.py waves <repo>` → `system-context/WAVES.md`: волны изменений без общих файлов —
    их можно отдать dev-агентам одновременно; общие файлы — по очереди.

11. **Отчёт.** Где пакет, какие возможности меняются, сколько пунктов влияния и как решены (задачи / не затрагивается), блокирующие вопросы
    (их — в чат: без ответа dev-агентам рано), число задач, волна, что дальше: «отдать dev-агенту: `openspec/changes/<id>/tasks.md`».

## Ключевые правила

- **Планируем, а не пишем код.** Пакет — это ТЗ для dev-агента: всё, что ему придётся угадать, — дыра в плане.
- **Влияние — из слоя, не по памяти.** Вызывающих, копии полей и подписчиков считает скрипт; модель решает, что с каждым делать.
  Пункт без решения — забытый клиент или потерянное поле.
- **Спека описывает поведение после изменения, «как будет».** Основная спека не правится: дельта ляжет в неё при архивации.
- **Блокирующий вопрос не решается молча.** Допущение — в дельте пометкой, вопрос — в proposal, человеку — в чат.
- **Задача исполнима без угадывания:** место (файл, `Класс.Метод`), что сделать, критерий «готово». Общие «доработать бэкенд» не годятся.
- **Не трогай чужое.** Код, основные спеки, слой sa-scan — только чтение; пишешь в `openspec/changes/<id>/` и `system-context/WAVES.md`.
- Подробно: [references/rules.md](references/rules.md).

## Результат

```
openspec/changes/<id>/
  proposal.md         Why, What Changes, Влияние, Открытые вопросы, Impact
  specs/<cap>/spec.md дельты: ADDED / MODIFIED (целиком, со всеми сценариями) / REMOVED
  design.md           контекст, решения, данные и контракты «было → стало», риски, проверка
  tasks.md            задачи для dev-агентов: место в коде + «готово, когда»; последние — проверка и обновление слоя
  impact.md           пункты влияния с решениями (собирает change.py analyze, решения — модель)
  impact.json         то же для скриптов (волны, пересечения)
system-context/WAVES.md  (если изменений несколько) волны без общих файлов
```

Дальше: dev-агент реализует `tasks.md` (сам или через `openspec-apply-change`), после слияния изменение архивируется
(`openspec archive <id>`) — дельта ложится в основные спеки, слой пересобирается (sa-scan).

## Если что-то не так

| Симптом | Что делать |
|---|---|
| `нет слоя sa-scan` | сначала скилл sa-scan; без слоя — план по коду вручную, и скажи, что влияние не посчитано |
| `layer`: «слой мог устареть» | сверь затронутые места с кодом (`grep`); в отчёте — предложить sa-scan, режим C |
| `find` ничего не нашёл | возьми слова из GUIDE.md (таблица «Возможности») или открой карточки глазами |
| `analyze`: «нет возможностей …» | id — из списка в сообщении (как в plan.json) |
| `analyze`: «сущности … нет» | имя — как в `system-context/data.md` (`### \`Order\``) |
| в impact.md нет вызывающих, а клиент точно есть | вызов собран динамически — допиши пункт `X-01` сам и предложи пересобрать контракты (sa-scan) |
| `check`: «MODIFIED заменяет требование целиком» | `change.py req … "<Имя>"` и перенеси все сценарии с теми же именами |
| `check`: «требование … не названо ни в одной задаче» | впиши имя требования в «кавычках» в задачу, которая его реализует |
| `check`: «задачи … нет в tasks.md» | номер в решении не совпадает с задачей — поправь решение или добавь задачу |
| `check`: «не затрагивается без причины» | одной фразой — почему изменение его не задевает |
| `check`: «пересекается с …» | изменения делят файлы: `change.py waves`, не раздавать одной волной |
| `openspec validate` ругается, свой разбор — нет | верь CLI: правь по его сообщению |

## Пример

**Запрос:** «Пусть покупатель сможет отменить и оплаченный заказ, деньги вернём через Stripe».
**Ход:** `layer` (слой свежий, 2 блокирующих вопроса) → `find` → `order-cancellation` →
`new cancel-paid-by-customer` → `analyze --cap order-cancellation --entity Order`: место создания заказа, миграция, Q-004 «может ли покупатель
сам отменить оплаченный» → дельта MODIFIED «Отмена заказа покупателем» (оба сценария, второй переписан) → proposal с Q-004 в «Открытые вопросы»
→ 9 задач → решения → `check`: 0 ошибок → в чат: Q-004 нужен ответ владельца до разработки.

- [examples/01-cancel-paid-order.md](examples/01-cancel-paid-order.md) — полный проход по фикстуре сервиса заказов
- [examples/02-tasks-bad-good.md](examples/02-tasks-bad-good.md) — задачи и влияние: плохо и хорошо
