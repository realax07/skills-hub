# ar-rules

Принцип — правило, которое действует для многих систем и проверяется: «сервис не читает чужую базу», «внешний вызов — с таймаутом
не больше 5 с», «возврат денег — с ключом идемпотентности». Слабой модели готовое правило полезнее собственного архитектурного
решения: dev-агент читает его перед задачей, sa-change проверяет по нему план, скрипт — код.

Механика — `scripts/rules.py`: кандидаты из документов, хранение принципов, проверки, нарушения, копия в проекты.
Твоя работа — суждение: что из сказанного в документах — правило, как его сформулировать проверяемо, что на самом деле нарушение.

## Как выполнять

- Команды — из корня рабочей папки, без `cd`; `<skill>` — папка этого скилла, `<arch>` — слой ar-scan (`architecture/`).
- Это одна непрерывная работа — от шага 1 до отчёта. Промежуточную сводку не пиши.
- Код и документы только читаешь. Пишешь в `<arch>/` и, на шаге 9, — в проекты.
- `principles.json` и `principles.md` не правь руками: `rules.py add`, `edit`, `except`.

## Процесс

1. **Слой ar-scan.** Нужны `<arch>/sources.json` и `landscape.json`. Нет — сначала скилл ar-scan (без ландшафта проверять нечего).
   Документы с правилами не добавлены в ландшафт — `python3 <ar-scan>/scripts/landscape.py add-docs <arch> <папка>` и `build`,
   или передай их здесь: `--docs <папка>` в шаге 2.
2. **Кандидаты:** `python3 <skill>/scripts/rules.py scan <arch> [--docs <папка>]` → `<arch>/RULE-CANDIDATES.md`: решения ADR и фразы
   «должен», «запрещено», «только», MUST/SHOULD со ссылкой `документ:строка`.
3. **Принципы.** Прочти кандидатов и документы вокруг них. Принцип — правило **для многих систем**, нарушение которого что-то ломает:
   деньги, данные, отказоустойчивость, безопасность, совместимость. Не принцип — описание поведения, план, пожелание
   («стараемся писать тесты»), частность одной системы. Для каждого принципа:
   ```
   python3 <skill>/scripts/rules.py add <arch> --title "<коротко>" --rule "<одно проверяемое предложение>" --why "<что сломается без него>"
     --area <интеграция|данные|деньги|надёжность|безопасность|наблюдаемость|выкатка|код> --applies <events,http,data,money,security,all>
     --source <документ:строка | чат> [--systems all|<id,id>] --check <no-shared-db | timeout --max 5 | grep … | review --question "…">
   ```
   Пользователь сказал правило в чате («у нас все вызовы с ретраями») — тоже принцип, `--source чат`.
   Затем в RULE-CANDIDATES.md у каждого кандидата **Решение**: `принцип P-03`, `дубль P-03` или `не принцип: <почему>`.
4. **Как проверить** — самое важное поле: правило без проверки забудут.
   - `no-shared-db` — общие базы данных из ландшафта;
   - `timeout --max N` — у внешних HTTP-вызовов в коде таймаут задан и не больше N секунд;
   - `grep --pattern '<regex>' --mode must|must-not [--files '*payment*']` — обязательный или запрещённый шаблон в коде систем;
   - `review --question "<вопрос>"` — скриптом не проверить: вопрос, который задаёт себе автор дизайна и ревьюер
     («что будет, если событие придёт дважды?»). Вопрос можно добавить и к скриптовой проверке.
   Шаблон grep — простой и узкий: лучше найти меньше, чем завалить ложными нарушениями. Подробно — [references/rules.md](references/rules.md).
5. **Проверка кода:** `python3 <skill>/scripts/rules.py verify <arch>` → `<arch>/VIOLATIONS.md`.
6. **Нарушения — сначала разбор, потом решение.** По каждому пункту: `**Проверка:**` — открой место, что увидел (`репозиторий:путь:строка`);
   `**Решение:**` — `нарушение: <что не так, что делать, кому>`, `исключение: <почему этой системе можно>`
   (и заведи: `rules.py except <arch> P-01 --system <id> --reason "…" --source <Q-… | документ | чат>`), `ложное: <почему проверка ошиблась>`
   или `вопрос Q-…` (`rules.py q <arch> --title "…?" --category … --seen … --affects … --assume … --who …`; категории — как у ar-scan).
   Исключение без источника — не исключение: решает архитектор или владелец, а не ты.
7. **Противоречия.** Два документа говорят разное (ADR — «только Kafka», вики — «можно REST между сервисами») — один принцип
   по более новому принятому источнику и вопрос; молча не выбирай.
8. **Проверка слоя:** `python3 <skill>/scripts/rules.py check <arch>` — 0 ошибок. После правок принципов — `verify`, потом `check`.
9. **В проекты** — если пользователь просил или согласился: `rules.py link <arch> <репозиторий>` на каждый репозиторий:
   `system-context/principles.md` (правила для его систем, исключения, текущие нарушения), `principles.json` (для sa-change)
   и указатель в `AGENTS.md` — dev-агент читает их перед задачей. Не просил и спросить некого — в отчёте команды.
10. **Отчёт в чат:** принципов (сколько проверяется скриптом), нарушений по принципам и как решены, исключения, вопросы целиком
    (до 7), противоречия документов.

## Ключевые правила

- **Одно правило — одно проверяемое предложение.** «Обеспечивать надёжность» — не правило; «внешний вызов — с таймаутом не больше 5 с» — правило.
  Слабая модель выполнит то, что можно проверить, и проигнорирует лозунг.
- **Почему — обязательно.** Без причины правило нарушат в первом же «особом случае»; с причиной модель сама поймёт, что случай не особый.
- **Источник — у каждого принципа и исключения.** Принципы придумываешь не ты: документ, слова пользователя или вопрос.
- **Нарушение решает человек.** Ты подтверждаешь или опровергаешь находку скрипта и говоришь, что делать; исключение заводится только
  с источником решения.
- **Немного сильных правил лучше многих слабых.** 8–15 принципов прочтут; 60 — нет. Частности одной системы — в её карточке ar-scan, не сюда.

## Формат результата

```
<arch>/
  principles.json      принципы (только командами rules.py)
  principles.md        их вид для людей и агентов, по областям
  RULE-CANDIDATES.md   кандидаты из документов с решениями
  VIOLATIONS.md        нарушения с проверкой и решением
  QUESTIONS.md         вопросы (общий с ar-scan)
<repo>/system-context/principles.md, principles.json   после link
```

## Пример

**Запрос:** «Вот ADR и страница стандартов из Confluence. Собери из них правила для агентов и проверь, кто их уже нарушает».
**Результат:** 8 принципов из 10 кандидатов (один — дубль, один — не принцип); проверяются скриптом 4: общая база (уведомления читают
базу заказов — исключение до ответа на вопрос), таймауты (вызов платежей без таймаута, Stripe и SendGrid по 10 с при лимите 5),
идемпотентность платежей (ключа нет — нарушение, команда Billing), секреты в коде (чисто). Разбор — [examples/01-adr-and-standards.md](examples/01-adr-and-standards.md).

## Если что-то не так

| Симптом | Что делать |
|---|---|
| «нет sources.json» | сначала ar-scan: `landscape.py init/add-repo/add-docs/build` |
| Кандидатов ноль | документы не добавлены — `add-docs` в ландшафт или `scan --docs`; правила из чата — `add --source чат` |
| grep находит сотни мест | шаблон слишком широкий — сузь `--pattern` и `--files` через `edit`, затем `verify` |
| timeout: «без таймаута», а он задан общим клиентом | решение `ложное: таймаут задан в <путь:строка>`; повторяется — `--check review` с вопросом |
| Владелец общей базы тоже в нарушениях | нарушает читающий; у владельца — `ложное: владелец базы`; читающему — исключение или нарушение |
| `check`: «принципы менялись после verify» | `verify`, потом `check` |
