## Что считать системой

Система — то, что **разворачивается отдельно** и с чем другие общаются по сети или через брокер: сервис, воркер, планировщик,
клиентское приложение (веб, мобильное), шлюз, внешний SaaS, легаси без репозитория. Не система: библиотека, общий код
(шина, настройки по умолчанию), тесты, хост развёртывания (Aspire AppHost, helm-чарт), утилиты сборки.

- Репозиторий с одним сервисом — одна система (`split=repo`). Монорепозиторий с несколькими пакетами, у которых есть входы,
  — система на пакет (`split=packages`); `auto` выбирает сам: два и больше пакета с входами → по пакетам.
- Пакеты без входов (домен, инфраструктура) скрипт отдаёт системе, которая на них ссылается (ProjectReference) или с тем же
  префиксом имени (`Ordering.Domain` → `Ordering.API`). Общий для многих пакет — не система: его код связей не даёт.
- API и его воркер: отдельно, если выкатываются отдельно (свой процесс в AppHost или compose); `--merge-into`, если документ называет их одной системой.
  Общая база у них — пункт сверки в любом случае.
- Имя: id — kebab-case, как в коде; имя из документов — алиасом, чтобы схемы и тексты сопоставлялись. `--rename` — если id неудачный
  (старый id станет алиасом).

## Как скрипт находит связи

| Вид | Откуда | Чем может ошибиться |
|---|---|---|
| Событие | публикация (`Publish`, `producer.send("тема")`, `new XEvent` рядом с отправкой) и подписка (обработчик, `subscribe`, `KafkaConsumer`) с тем же именем события или темы во всех репозиториях | тема собрана из переменной — не видна; одно имя у разных событий |
| HTTP | префикс входа владельца (`/api/orders`) строкой в коде другой системы | общий префикс у двух систем — связи нет (неоднозначно); путь собран из частей |
| gRPC | клиент `XClient` / `XServiceClient` сервиса `X` в коде другой системы | клиент через общий пакет |
| Адрес | хост с именем системы (`http://payments:8000`, `catalog-api`), настройка `PAYMENTS_URL`, `services__x__…`, `Identity__Url` | имя настройки не похоже на систему |
| Развёртывание | Aspire `WithReference` и адрес в `WithEnvironment`, compose `depends_on` и адреса в `environment` | `WaitFor` — порядок запуска, не вызов: скрипт его не считает |
| Данные | база в AppHost у двух проектов, `ConnectionStrings:X`, `X_DB_URL` у двух систем | разные базы на одном сервере — проверь имя базы |
| Внешнее | хост в коде (не в комментарии), не сопоставленный с системой | тестовый или документационный адрес |

Это эвристики. Связь в карточке — со ссылкой на место в коде: сомневаешься — открой.

## Документы

- Скрипт разбирает: mermaid (flowchart и sequence), PlantUML (включая C4 `Rel(...)`), Structurizr DSL, AsyncAPI 2 и 3,
  HTML-выгрузки (Confluence) — в текст. ADR узнаёт по папке `adr/` или по заголовку и строке «Статус».
- Схема даёт связи сама. Текст читаешь ты: назначение, владелец, SLA, связи словами — `claim` со ссылкой `документ:строка`.
  Одна связь — одно утверждение. Связь «A берёт данные B из его базы» — `--kind data`.
- Документы о многих системах (общая схема) читай целиком; страницу одной системы — для её назначения и владельца.
- Устаревший документ («Обновлено: 2019») — его утверждения всё равно записывай: расхождение с кодом и есть ценность сверки.

## Сверка

`RECONCILE.md` — пункты по видам. Решение пишется после проверки, не по заголовку пункта.

| Вид | Что проверить | Типичное решение |
|---|---|---|
| Документ без кода | есть ли в коде вызывающего адрес, клиент, публикация (поиск по имени системы, теме) | сделано иначе → `ок:` с местом; не сделано → `ок: план, в коде нет …` или вопрос, если от этого зависит поведение |
| Код без документа | зачем вызов; документ просто не полный? | `ок: документ не описывает …, в коде … (путь)` |
| Событие без подписчика | подписчик вне ландшафта? репозиторий не добавлен? | вопрос «кто потребляет X» — внешний потребитель ломается молча |
| Подписка без издателя | издатель вне ландшафта, другое имя, мёртвая подписка | вопрос или `ок:` с найденным издателем |
| Подписчик ждёт поле, которого издатель не шлёт | копии события разошлись | вопрос, блокирует: подписчик получает пустое поле |
| Общая база | читают или пишут? чьи таблицы? запрещено ли ADR | вопрос; `ок:` только если документ явно разрешает |
| Узел схемы без системы | система под другим именем, внешняя, не система (человек, «Интернет») | алиас или `--external` и `build`; человек на схеме — `не связь: пользователь, не система` |
| Адрес вне ландшафта | внешний сервис или тестовый адрес | `--external --alias хост` и `build`; пример — `не связь:` |

- `ок:` и `не связь:` — от 25 символов: что проверил и где. «ок: так задумано» — не решение.
- Пункты, у которых вызывающая сторона без репозитория в ландшафте (витрина из документа), в сверку не попадают:
  их по коду не проверить — они видны в `landscape.md` как «только в документе».

## Связи и карточки

- «Зачем и как» в `landscape.md` — для того, кто меняет одну из двух систем: зачем связь, синхронно или событием, что при отказе
  (таймаут, повтор, заказ остаётся в статусе …). Лучший источник — `system-context/integrations.md` слоя sa-scan («При отказе»).
- Карточка `systems/<id>.md` — то, что откроет dev-агент перед изменением системы. Блок `sa:auto` — данные; под ним — «Заметки»:
  SLA, окна выкатки, кто согласует контракт. Заметка без источника — предупреждение `check`.
- `link` кладёт копию карточек в проект. Копия устаревает — после пересборки слоя `link` снова.

## Вопросы

Формат и категории — как у sa-scan (`QUESTIONS.md`, поле «Ответ» для человека). Хороший вопрос — про внешний мир и договорённости:
«кто потребляет X», «можно ли уведомлениям читать базу заказов», «кто владелец». Не вопрос — то, что видно в коде:
открой и проверь. `--affects` — id систем; по ним вопрос попадает в карточки.

## Обновление

- `status` — какие репозитории ушли вперёд по git, какие документы менялись после сборки.
- Новый репозиторий — `add-repo`, `build`. Решения в `RECONCILE.md` сохраняются по ключу пункта; новые пункты — без решения.
  Исчезнувшая система (переименована, исключена) — карточка помечается ⚠, удали её, если заметки не нужны.
- Заметки вне блоков `sa:auto` и «Зачем и как» переживают пересборку.

## Крайние случаи

| Случай | Как быть |
|---|---|
| Только документы, кода нет | `add-docs`, системы — `system <id> --title` по документу; сверки с кодом не будет, связи — «только в документе»; в отчёте так и написать |
| Только код, документов нет | сверка «код без документа» не строится; назначение — по коду (`--source код`), владелец — вопрос |
| Огромная выгрузка Confluence | читай документы о связях (схемы, «Интеграции», «Архитектура») и страницы систем; остальное — по индексу «Документы» при необходимости |
| Одно событие с разными именами в системах (`OrderPaid` и `order.paid`) | `claim --kind event` со ссылкой на оба места и `ок:` в сверке; переименовывать в коде — не твоя задача |
| Связь через общий файл, FTP, выгрузку | `claim --kind data` со ссылкой на документ или код |
| Репозиторий недоступен (нет папки) | `build` пропустит его с предупреждением; в отчёте — что не проверено |

## Типичные ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| Назначение «сервис заказов» без источника | не проверить, может быть неверно | `--source документ:строка` или `код` |
| Владелец «команда Billing» из головы | изменения пойдут согласовывать не туда | из документа или вопрос |
| Общая база — «ок: так исторически» | следующее изменение схемы сломает соседа | вопрос со ссылкой на ADR, если он есть |
| Узел «CRM» решён `ок:` | система не появилась в ландшафте, связи с ней не видно | `system crm --external`, `build` |
| Правка `sources.json` или блоков `sa:auto` руками | перезапишется или сломает разбор | команды `landscape.py`, заметки вне блоков |
| Решения написаны до проверки | «ок» на настоящую поломку | сначала открыть места из пункта, потом решать |
