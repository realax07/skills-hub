Тестирование · qa-scan

qa-scan: тест-кейсы из TMS — в репозиторий, и md становится главным

Скилл переносит тест-кейсы из Test IT, Zephyr Scale, TestRail или TestLink в md внутри проекта: файл на кейс, иерархия TMS папками, общие шаги, параметры, требования, автотесты. Секреты из шагов скрываются до записи на диск, а агенты получают роутинг — как найти кейсы под задачу по возможности, файлу кода, требованию или тегу.

Что даёт

Кейсы в TMS агент не видит: ни при доработке, ни при написании автотестов, ни при сверке со спекой. После переноса это файлы рядом с кодом, с картой и индексами, которые влезают в контекст даже слабой модели.

Кейс — md-файл

test-cases/<раздел>/TC-0001-<slug>.md: front-matter (приоритет, статус, теги, требования, возможности, код, автотесты, откуда из TMS) и разделы «Цель», «Предусловия», «Шаги» с «Ожидается», «Параметры». Номер TC-0001 постоянный.

Роутинг для агентов

ROUTING.md (~3 тыс. токенов) и _index/: кейсы по возможностям sa-scan, по файлам кода (через trace.md), по требованиям, тегам, автотестам. route.py find — то же одной командой.

Секреты не уходят в git

Пароли, токены, ключи, реальные карты из шагов скрываются в fetch.py до записи на диск: [скрыто: S-01]. В QUESTIONS.md — где они были, без значений. check.py ловит и вписанные позже руками.

Связь со спекой и кодом

map.py auto ставит кейсам возможности из openspec/ и находит автотесты по аннотациям (TC-0001, C123, SHOP-T12, WorkItemIds). Пробелы видны сразу: «у order-payment 0 кейсов».

Качество — отчётом, а не правкой

QUALITY.md: дубли, шаги без ожидаемого, «Работает» вместо результата, картинки-ссылки на TMS. Кейсы не переписываются — это решение владельцев тестов.

md первичен, но переезд бывает долгим

Повторный импорт обновляет только то, что не правили в md; правленое и изменённое в TMS — конфликт на решение человека. Исчезнувшие из TMS кейсы не удаляются.

Когда звать

Когда команда уходит из TMS в репозиторий или хочет, чтобы агенты видели тест-кейсы.

Подходит

  • Есть ссылка на TMS или файл выгрузки, и кейсы нужны в репозитории в markdown.
  • Агенты дорабатывают проект и должны знать, какие кейсы проверяют меняемое поведение.
  • Нужно связать тест-кейсы со спекой (sa-scan) и автотестами, найти непокрытые возможности.
  • Переезд идёт постепенно: в TMS ещё правят, в md уже правят — режим обновления.

Не подходит

  • Написать автотесты по кейсам — это следующий шаг, не этот скилл.
  • Прогоны, результаты, отчёты о тестировании — их TMS хранит сама, скилл переносит только дизайн тестов.
  • Zephyr Squad и Zephyr Enterprise по API — только через выгрузку CSV/xlsx.

Как работает

Всё механическое — скрипты на Python без зависимостей: разбор форматов, HTML → md, номера, хеши, индексы, поиск секретов. Модель решает спорные сопоставления и пишет отчёт, человек — секреты, ПДн и конфликты.

Как результат используется потом

Агент доработки

AGENTS.md → ROUTING.md → _index/by-capability.md или grep по by-code.md → читает 3–15 кейсов, а не тысячи. Меняет поведение — обновляет кейсы вместе с кодом.

Агент автотестов

Берёт шаги и «Ожидается» как сценарий, номер TC-0001 — в аннотацию теста; map.py autotests потом найдёт связь.

Тестировщик

Правит кейсы в md через ревью, как код; видит дубли и размытые кейсы в QUALITY.md.

Человек (лид)

Решает по QUESTIONS.md: откуда брать секреты, реальные ли ПДн, какой версии верить при конфликте.

Главные правила

Почему скилл ведёт себя так, а не иначе.

  • Перенос, а не переписывание.Кейсы — договорённость команды о том, что проверять. «Причёсанные» агентом 500 кейсов незаметно меняют смысл; замечания — в QUALITY.md.
  • Секреты скрываются до записи на диск.Репозиторий живёт годами и читается всеми, у кого есть доступ к коду. Значения не попадают ни в md, ни в снимок, ни в отчёт.
  • Токен — переменной окружения.Не в чат и не в файлы: переписка и логи агента сохраняются.
  • Номер TC постоянный.На него ссылаются автотесты и задачи; номера удалённых кейсов не переиспользуются.
  • Правки в md важнее TMS.Повторный импорт не перезаписывает правленое; конфликт решает человек.
  • Сопоставление — только уверенное.Неверная возможность уводит агента к не тем кейсам, а пустая видна в отчёте.
