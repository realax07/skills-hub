# Пример 2. Плохо / хорошо: доступ, «улучшения», сопоставление

## Запрос

> перенеси наши тесты из Test IT https://testit.acme.ru, проект 12, нужно чтобы агенты их видели. кейсы там местами кривые, поправь заодно

## Плохо

1. «Пришлите, пожалуйста, приватный токен Test IT» — токен оказывается в переписке и в логах агента.
2. Агент вызывает API сам через curl, читает JSON и пишет md-файлы руками: без маскировки секретов, без хешей и постоянных номеров,
   с собственной разметкой шагов. Повторный импорт потом всё перетрёт.
3. «Заодно поправить»: агент переписывает ожидаемое «Работает» на «Заказ создан, статус NEW», объединяет «дубли», переводит
   англоязычные кейсы. В диффе 300 изменённых кейсов, проверить их никто не сможет.
4. Возможности назначены всем кейсам раздела «Корзина», хотя половина там — про промокоды из другой возможности.
5. В отчёте: «Готово, всё перенёс и улучшил».

## Хорошо

1. Попросить задать токен в терминале, а не присылать его:
   > Задайте, пожалуйста, токен в своём терминале перед запуском агента: `export TESTIT_TOKEN=…` (Профиль → Приватный токен).
   > Присылать его сюда не нужно. Если токена нет, выгрузите проект в xlsx — перенесу из файла.
2. Перенос — скриптами, пробный прогон на большом проекте:
   ```bash
   python3 <skill>/scripts/fetch.py api . --tms testit --url https://testit.acme.ru --project 12 --limit 50
   python3 <skill>/scripts/build.py .
   ```
   Посмотреть 3–5 кейсов разных разделов, потом без `--limit`.
3. «Поправить» — отдельным шагом и только с согласия: сначала перенос как есть, потом `lint.py` и предложение:
   > В `QUALITY.md`: у 41 кейса ожидаемое «Работает» или пусто, 6 пар дублей. Переносил как есть. Если нужно — поправлю
   > по списку отдельным коммитом, чтобы правки было видно в диффе. С каких начать?
4. Сопоставление по разделам — только однородные (`map.py set --section korzina --cap cart`), смешанные — по одному; где не ясно — пусто.
5. В отчёте — цифры и решения, которые нужны от человека (секреты, ПДн, дубли, конфликты), и что коммитить.

## Почему

Перенос, который можно проверить, ценнее «улучшенного», который проверить нельзя: кейсы — договорённость команды о том,
что проверять. Секреты и токены, однажды попав в git или в историю чата, считаются утёкшими.
